# 일자 배정과 이동 시점 — 설계 정의 (논의용)

> 아직 구현하지 않았다. 이 문서를 보고 보완할 점을 정한 뒤에 들어간다.

## 0. 왜 바꾸나

지금은 **하루 = 한 도시**다. 그래서 세 가지가 어긋난다.

1. 볼거리가 반나절치인 도시도 하루를 통째로 먹는다 (`Math.max(1, …)`)
2. 도시 간 이동은 **언제나 아침 첫 편**이다. 선택지가 없다
3. 3단계는 '볼거리 시간 합', 4단계는 '달력 칸'을 세면서 **둘 다 "일"이라고 부른다**
   (같은 여행이 8.7일 ↔ 15칸)

셋 다 뿌리가 같다 — **하루를 시간 축으로 보지 않고 칸으로 봤다.**

---

## 1. 기본 개념

### 1-1. 하루는 시간 축이다

하루에는 세 가지가 들어간다.

| | 무엇 | 예 |
| --- | --- | --- |
| **체류** | 한 도시에서 볼거리를 보는 시간 | 톨레도 4시간 |
| **이동** | 도시 간 이동 (door-to-door) | 마드리드→톨레도 88분 |
| **여백** | 식사·휴식·줄서기 | 이미 예산에 반영 |

### 1-2. 하루 예산

```
하루 볼거리 예산 = dailyMinutes(prefs) − 그날의 도시 간 이동 시간
```

`dailyMinutes` 는 지금 것을 그대로 쓴다 (보통 **504분 = 8.4시간**, 반나절 252분).
바뀌는 것은 **이동이 이 예산을 먹는다**는 점이다. 지금은 이동이 예산 밖에 있어서,
2시간 이동한 날도 8.4시간짜리로 계산됐다.

```
예: 마드리드 → 세비야 197분 이동
    그날 볼거리 예산 = 504 − 197 = 307분 (약 반나절 반)
```

이 한 줄이 3단계와 4단계가 갈라지던 원인을 없앤다.

### 1-3. 도시별 볼거리 분량 (실측)

| 도시 | 채택선 넘는 곳 | 분량 |
| --- | --- | --- |
| 마드리드 | 54곳 | 10.9일치 |
| 바르셀로나 | 53곳 | 9.6일치 |
| 세비야 | 19곳 | 3.3일치 |
| 그라나다 | 15곳 | 3.0일치 |
| 톨레도 | 10곳 | 2.2일치 |
| 코르도바 | 9곳 | 1.7일치 |
| 몬세라트 | 5곳 | 1.1일치 |
| 세고비아 · 아빌라 | 4~5곳 | 0.9일치 |
| 론다 | 4곳 | 0.5일치 |
| 네르하 · 시체스 | 2곳 | 0.4일치 |

**반나절 이하인 도시가 실제로 많다.** 이들을 하루씩 주는 것이 지금의 낭비다.

## 2. 원칙 A — 날 채우기 (day packing)

날을 하나씩 만들면서 예산이 찰 때까지 넣는다.

```
새 날을 연다 → 예산 = 504분
  1. 지금 있는 도시의 남은 볼거리를 넣는다
  2. 그 도시가 끝났고 예산이 남으면:
       다음 도시로의 이동 시간 T 를 예산에서 뺀다
       남은 예산 ≥ 최소체류(90분) 이면  → 오늘 옮긴다. 2번을 반복
       아니면                          → 오늘은 여기서 끝. 내일 아침 이동
  3. 예산이 차면 날을 닫는다
```

**최소체류 90분**: 옮겨 가서 한 곳도 제대로 못 볼 시간이면 옮기는 의미가 없다.
(대표 명소 하나가 보통 60~90분)

### 예 — 마드리드 이후 톨레도·세고비아 (당일치기 아님, 실제로 옮겨 다니는 경우)

```
Day 1  마드리드 504분                        → 예산 0
Day 2  마드리드 504분                        → 예산 0
Day 3  마드리드 남은 것 200분
       → 톨레도 이동 88분 (예산 504−200−88=216)
       → 216 ≥ 90 이므로 오늘 옮긴다. 톨레도 216분
Day 4  톨레도 남은 것 879분? → 아니, 2.2일치 중 216 썼으니 남은 것부터
       …
```

### 예 — 반나절 도시 둘 (지금 2칸 → 앞으로 1칸)

```
론다 0.5일치(237분) + 네르하 0.4일치(216분), 론다→네르하 이동 60분
Day n  론다 237 + 이동 60 + 네르하 207 = 504분  → 한 날에 들어간다
```

## 3. 원칙 B — 이동 시점 세 가지

이동을 하루의 **어디에** 놓을지. 세 가지만 둔다.

| 시점 | 하루 모양 | 언제 좋은가 |
| --- | --- | --- |
| **아침 이동** | 이동 → 새 도시 온종일 | 이동이 길다 · 새 도시에 볼 것이 많다 |
| **오후 이동** | 오전 현재 도시 → 점심 → 이동 → 저녁 새 도시 | 이동이 중간 · 현재 도시에 반나절이 남았다 |
| **저녁 이동** | 하루를 현재 도시에서 다 쓰고 → 저녁에 옮겨 잠만 잔다 | 이동이 짧다 · 내일 새 도시를 아침부터 쓰고 싶다 |

### 3-1. 자동 선택 규칙

```
T = 이동 시간(door-to-door)
A = 현재 도시에 남은 볼거리 시간

T ≤ 90분  이고 A ≥ 250분   →  저녁 이동
T ≤ 180분 이고 A ≥ 150분   →  오후 이동
그 밖                       →  아침 이동
```

**왜 이 숫자인가**

- **90분** — 저녁 이동은 식사 후에 움직여 잠만 자는 것이다. 90분을 넘으면
  자정 가까이 도착한다(저녁식사 20:30 시작 → 22:00 출발 → 23:30 도착).
  실제 데이터에서 마드리드↔톨레도 88분, 마드리드↔세고비아 84분,
  바르셀로나↔시체스 84분이 여기 들어온다.
- **180분** — 오후 이동은 점심(13:00~15:30) 뒤에 움직인다. 15:30 출발 +
  3시간 = 18:30 도착이면 저녁 일정 하나와 저녁 식사가 가능하다. 그 이상이면
  도착해서 저녁만 먹게 되므로 아침에 옮기는 편이 낫다.
  세비야↔코르도바 100분, 코르도바↔그라나다 129분, 바르셀로나↔지로나 121분이 여기.
- **A ≥ 250분 / 150분** — 현재 도시에 반나절(252분) 또는 세 시간이 남았을 때만
  '더 보고 옮기는' 선택이 뜻이 있다. 남은 게 30분이면 그냥 아침에 옮긴다.
- 마드리드↔세비야 197분, 마드리드↔바르셀로나 229분, 바르셀로나↔발렌시아 233분은
  전부 **아침 이동**으로 떨어진다. 지금과 같다.

### 3-2. 언제나 지키는 제약

1. **야간 도착 금지** — 숙소 도착이 23:30 을 넘으면 그 시점은 후보에서 뺀다.
2. **첫날** — 공항 도착 시각이 하루의 시작이다. 이동 시점을 고를 여지가 없다.
3. **마지막 날** — 출국 시각이 마감이다. 그날 도시를 옮기지 않는다.
4. **실제 시간표 우선** — 고른 시점의 시간대에 실제 편이 없으면 그 다음 편으로
   미루고, 그날 남은 편이 없으면 다음 후보 시점으로 넘어간다.

### 3-3. 사용자가 바꿀 수 있다

4단계 여정에서 이동 구간마다 **[아침 · 오후 · 저녁]** 토글을 준다.
기본값은 자동 선택이고, 왜 그렇게 골랐는지 한 줄로 적는다.

```
마드리드 → 톨레도   [아침] [오후] ●저녁    88분 · 저녁에 옮겨 내일 아침부터 톨레도
```

바꾸면 그 구간부터 일정이 다시 짜인다. 불가능한 선택지는 이유와 함께 잠근다
("이 시각에는 남은 편이 없습니다").

## 4. 원칙 C — 당일치기도 반나절이 될 수 있다

지금 당일치기는 **무조건 1칸**이다. 앞으로는 예산으로 다룬다.

```
당일치기 비용 = 왕복 이동 + 그 도시 볼거리 시간
남는 예산이 있으면 같은 날 거점 일정을 이어 붙인다
```

```
예: 마드리드 거점, 세고비아 당일치기
    왕복 168분 + 세고비아 0.9일치(447분) = 615분 > 504  → 하루 꽉 참
예: 마드리드 거점, 네르하 당일치기
    왕복 X분 + 네르하 0.4일치(216분)  → 남는 예산으로 마드리드 저녁 일정
```

**짐을 옮기지 않는다**는 당일치기의 정의는 그대로 둔다. 바뀌는 것은
'하루를 통째로 먹는다'는 가정뿐이다.

## 5. 원칙 D — 3단계와 4단계가 같은 계산을 쓴다

3단계의 "예상 N일"을 **이 날 채우기를 실제로 돌린 결과**로 바꾼다.
그러면 두 화면이 구조적으로 어긋날 수 없다.

3단계 표시(안):

```
43곳 선택 · 볼거리 8.7일치 → 일정 11일 필요 (이동 2.3일 포함)
쓸 수 있는 14.8일 안에 들어갑니다
```

두 숫자를 다 두는 이유: **넘칠 때 해법이 다르다.** 볼거리가 많아 넘치면
아이템을 줄이고, 도시가 많아(이동이 많아) 넘치면 도시를 뺀다. 하나로 합치면
사용자가 무엇을 줄여야 하는지 알 수 없다.

4단계 표시(안): 항상 한 줄.

```
16일 계획 · 15일 사용 · 1일 여유
16일 계획 · 17일 필요 → 1일 모자람
```

## 6. 무엇이 바뀌고 무엇이 그대로인가

**바뀐다**

- `itinerary.ts` 의 `nights` 계산 (도시별 밤 수 → 날 채우기 결과)
- `planner.ts` 의 `scheduleFromItinerary` (칸 배정 → 시간 축 배치)
- 이동 시점 선택과 그 UI, 상태 저장(`moveTiming: Record<hop, 'morning'|'midday'|'evening'>`)
- 3·4단계 일수 표시

**그대로 둔다**

- 거점 판정(가중치 0.30/0.25/0.20/0.15/0.10, 당일치기 편도 120분)
- 순위(명성 0.40 + 대표 0.30 + 검증 0.30, 채택선 0.45)
- 코스 등급(꽉찬 4일치 / 보통 2일치 / 찍먹 3곳)
- 하루 안 배치(앵커 + 근접도, 슬롯 창)
- 미식 예외

**위험**

- 일정 관련 검사가 다수 깨진다. 기대값을 새 모델로 다시 잡아야 한다
- 저장된 계획의 호환(마이그레이션 필요)
- '당일치기'와 '하루에 두 도시'가 화면에서 헷갈릴 수 있다 — 말로 구별해야 한다

## 7. 정해야 할 것 (논의)

1. **문턱값** — 저녁 90분 / 오후 180분 / 최소체류 90분. 이 값이 맞는가?
2. **하루 최대 도시 수** — 제한을 둘 것인가? (2곳? 3곳? 무제한?)
   지금 규칙대로면 이동이 짧고 볼거리가 적은 도시가 이어지면 하루에 3~4곳도 가능하다
3. **저녁 이동의 성격** — '잠만 자러 옮긴다'로 볼 것인가, 도착 후 야식·야경 일정을
   허용할 것인가?
4. **자동 선택 vs 항상 물어보기** — 자동으로 고르고 바꿀 수 있게 할 것인가,
   아니면 이동마다 사용자가 정하게 할 것인가?
5. **3단계 표시** — 두 숫자(볼거리 / 일정) 병기가 맞는가, 하나로 갈 것인가?
