# 화면이 멈추던 진짜 원인 — 계획 생성의 무한 루프

## 증상

아이패드 사파리에서:

1. 첫 화면이 오래 걸리거나 뜨지 않는다
2. 갑자기 멈췄다가 화면이 잘리거나 검게 된다
3. 그 상태에서는 **아무것도 눌리지 않는다**

여섯 번 넘게 다른 원인을 짚었고 다 빗나갔다.

## 어떻게 잡았나

화면이 죽으면 사용자는 진단을 누를 수도 없다. 그래서 계기를 먼저 고쳤다
(→ `14-diagnostics.md`) — 멈춤 감시자, 페이지보다 오래 사는 기록, 다시
열리면 먼저 말하기. 그러자 다음 기록이 왔다.

```
   0.0s 정보 ─── 페이지 열림 02:52:04
  12.3s 눌림 톨레도
  12.5s 동작 도시 선택 toledo → 7곳
   0.0s 정보 ─── 페이지 열림 02:52:23
  33.9s 멈춤 자바스크립트가 20.3초 멈췄습니다 (메인 스레드 막힘)
```

**두 줄이 모든 것을 정했다.**

- `멈춤 … 메인 스레드 막힘` — 합성기·그리기 문제가 아니다. **자바스크립트가
  막힌 것이다.** 이 둘을 갈라 놓은 감시자가 아니었으면 계속 CSS 를 뒤졌을 것이다.
- `도시 7곳` — 그동안의 측정은 1~5곳이었다. 톨레도가 특별한 것이 아니라
  **일곱 번째 도시**였다.

도시를 늘려 가며 엔진만 따로 돌리자 다섯 곳에서 **10분이 지나도 끝나지
않았다.** `buildItinerary` 는 1~3ms 로 멀쩡했으므로 `buildPlans` 다.

## 원인

`planner.ts` — 남는 날을 숙박지에 나눠 주는 자리.

```ts
while (extra > 0) {
  // … 점수가 가장 높은 도시를 고른다
  if (given[best] + stop.nights >= Math.ceil(stop.itemDays) + 2) {
    if (sleepStops.every(/* 전부 배부른가 */)) break;
    weights[best] = 0.001;
    continue;                    // ← extra 가 줄지 않는다
  }
  given[best] += 1;
  extra -= 1;
}
```

배부른 도시를 **후보에서 빼지 않고 가중치만 낮췄다.** 그런데 점수는

```
weights[i] / totalW  −  given[i] / 남는날
```

이라, 아직 배부르지 않은 도시가 **하루라도 받으면 그 도시 점수가 음수로
내려간다.** 그러면 가중치를 0.001 로 낮춘 배부른 도시가 다시 1등이 되고,
배불러서 또 `continue` — 영원히 같은 자리를 돈다.

실제 값으로 확인한 것:

```
바르셀로나  6박 · 볼거리 3일치 → 배부름기준 5  → 이미 배부름
발렌시아    2박 · 볼거리 2일치 → 배부름기준 4
남는 날 2

1바퀴: 바르셀로나 배부름 → weights=0.001, extra 그대로 2
2바퀴: 발렌시아에 하루   → 남은 1
3바퀴: 바르셀로나 배부름 → weights=0.001, extra 그대로 1
…
200000바퀴: 그대로
```

점수를 실제로 계산해 보면 왜 빠져나올 수 없는지가 보인다.

```
바르셀로나  0.001/5 − 0/2 = +0.0002   ← 배부른데 1등
발렌시아    2/5     − 1/2 = −0.1
```

`buildPlans` 는 **1단계에서도** 돈다. 그래서 도시를 고르는 순간 메인 스레드가
통째로 막히고, 화면은 그리다 만 채 멈추고 아무것도 눌리지 않는다. 사파리가
오래 도는 스크립트를 끊으면 리액트가 그리다 만 자리에서 끊겨 **아래쪽이
빈 화면**이 된다. 보고된 세 증상이 전부 이것 하나였다.

## 고친 것

배부른 곳은 **후보에서 뺀다.** 그러면 매 바퀴마다 반드시 하루가 나가거나
(`extra` 감소) 더 줄 곳이 없어 끝난다. **끝나지 않을 수가 없다.**

```ts
const isFull = (i) => given[i] + sleepStops[i].nights >= Math.ceil(sleepStops[i].itemDays) + 2;

while (extra > 0) {
  let best = -1, bestScore = -Infinity;
  for (let i = 0; i < sleepStops.length; i++) {
    if (isFull(i)) continue;                 // 후보에서 뺀다
    const score = weights[i] / totalW - given[i] / Math.max(1, totalDays - schedule.length);
    if (score > bestScore) { bestScore = score; best = i; }
  }
  if (best < 0) break;                       // 더 줄 곳이 없다
  given[best] += 1;
  extra -= 1;
}
```

보고된 그 조합이 **10분 이상 → 20ms** 가 됐다.

## 왜 167개 검사가 못 잡았나

**화면 검사로는 잡을 수 없는 종류다.** 브라우저가 멈추면 검사도 함께 멈춘다
— 실패가 아니라 그냥 안 끝난다. 그리고 검사들이 쓰던 도시 조합(마드리드+
톨레도+세비야 같은)은 우연히 이 함정을 비껴갔다.

그래서 `scripts/planner-check.mjs` 를 새로 만들었다. 엔진만 따로 돌려
**시간 예산(400ms)** 을 걸고, 조합을 넓게 훑는다.

```
=== 보고된 그 조합 ===
  ✓ 20.1ms · 계획 3안
=== 넓게 훑기 ===
  훑은 조합 204가지 · 가장 오래 걸린 것 11.2ms
✓ 계획 생성 정상 — 모든 조합이 끝난다
```

되돌려 놓고 돌리면 60초 안에 끝나지 않는다(= 무한 루프 재현). 검사가 실제로
이 버그를 잡는다는 것을 확인했다.

## 남기는 교훈

1. **끝나지 않는 것은 느린 것과 다르다.** 성능을 잰다고 `buildPlans` 를
   여러 번 돌려 평균을 냈는데, 애초에 한 번도 안 끝나는 조합이 있었다.
   측정 자체가 그 조합을 비껴갔다.
2. **`continue` 가 있는 `while` 은 매 바퀴 진행이 보장되는지 봐야 한다.**
   여기서는 `extra` 를 줄이지 않는 경로가 하나 있었다.
3. **화면만 보는 검사로는 못 잡는 층이 있다.** 엔진은 엔진대로, 시간 예산을
   걸고 따로 돌려야 한다.
4. **증상이 보이는 층과 원인이 있는 층은 다르다.** '화면이 빈다 · 안 눌린다'
   는 그리기 문제처럼 보이지만, 멈춤 감시자가 `자바스크립트 막힘` 이라고
   찍어 주지 않았으면 계속 CSS 를 뒤졌을 것이다.
