# 하얀 화면과 낡은 캐시

> "처음 화면이 뜨는데 갑자기 시간이 오래 걸려. 혹은 계속 빈 화면으로 되어
> 있어" / "1단계에서 마드리드 선택 후 다른 선택지를 선택하려는데 더 이상
> 버튼이 눌러지지 않아"

깨끗한 브라우저에서는 재현되지 않았다. 배포된 파일도 손으로 만든 빌드와
바이트까지 같았다. 그래서 **브라우저에 남아 있는 것**을 의심했고, 거기서
두 가지가 나왔다. 하나는 고장의 원인이고, 하나는 고장을 하얀 화면으로
만드는 증폭기다.

---

## 1. 서비스 워커가 몇 주 전 데이터를 쥐고 있었다

```js
const CACHE = 'trip-planner-v1';          // 영원히 같은 이름
...
caches.match(request).then((hit) => hit ?? fetch(request))   // 모든 자원 캐시 우선
```

두 줄이 겹치면서 이렇게 된다.

- 이름이 바뀌지 않으니 `activate` 의 청소가 **아무것도 지우지 않는다.**
- 데이터도 캐시 우선이라, 한 번 받아 둔 `data/spain.json` 은 **새 배포가
  나가도 영원히 그대로다.**

문서(HTML)만 망 우선이라, **자바스크립트는 새것으로 바뀌고 데이터는 예전
것**이 된다. 새 코드가 예전 데이터를 읽는 상태다.

재현했다. 예전 판을 두 번 열어 캐시를 채운 뒤 서버 데이터를 60곳 → 42곳으로
바꾸고 다시 열면:

```
예전 판   캐시 trip-planner-v1              앱이 읽은 도시 수 60  ← 낡은 데이터
새 판     캐시 trip-planner-20260901…       앱이 읽은 도시 수 42  ← 새 데이터
```

### 어떻게 고쳤나

1. **캐시 이름에 배포 판 번호를 넣는다.** 워커를 `sw.js?v=<판번호>` 로
   등록하므로 배포마다 워커 주소가 달라지고, 다시 설치되면서 `activate` 가
   예전 캐시를 통째로 지운다. 낡은 데이터가 남을 자리가 없다.
2. **`data/` 는 망 우선**으로 바꿨다. 새것이 있으면 새것, 못 받으면 캐시.
   오프라인은 그대로 되고 낡지는 않는다.
3. **`assets/` 만 캐시 우선**으로 남겼다. 파일 이름에 내용 해시가 붙으므로
   내용이 바뀌면 이름이 바뀐다 — 낡을 수가 없는 것들이다.
4. 예전 워커가 쥐고 있던 페이지는 새 워커가 넘겨받는 순간 **한 번만** 다시
   불러, 새 코드가 예전 캐시를 읽는 한 번의 어긋남을 끝낸다.

---

## 2. 그리다 터지면 화면이 하얗게 비었다

리액트는 그리는 중에 오류가 나면 트리를 통째로 버린다. 받아 주는 곳
(오류 경계)이 없으면 남는 것은 **빈 `<div id="root">` 하나**다. 사용자에게는

- 처음부터 그렇다면 → "계속 빈 화면"
- 쓰다가 그렇다면 → "더 이상 버튼이 눌러지지 않아"

로 보인다. 무엇이 잘못됐는지도, 어떻게 빠져나오는지도 알 수 없다. 이 앱에는
경계가 **하나도 없었다.**

`Crashguard` 를 넣었다. 무엇이 잘못됐는지 적고, 빠져나갈 길을 넷 준다.

| 버튼 | 하는 일 |
| --- | --- |
| 다시 그려 보기 | 일시적인 문제면 이걸로 돌아온다 |
| 받아 둔 것 비우고 새로 받기 | 워커를 내리고 캐시를 지운 뒤 다시 받는다 (위 1번이 원인일 때 이걸로 풀린다) |
| 백업 파일 받기 | 고장난 상태에서도 계획을 잃지 않게 |
| 처음부터 | 위 셋으로 안 될 때. 고른 것은 사라진다 |

저장된 계획(localStorage)은 '비우고 새로 받기' 로도 지우지 않는다. 고치자고
사용자의 일정을 지울 수는 없다.

---

## 3. 덤 — 아무 말 없이 비던 목록

`loadItemsFor` 가 실패하면 `error` 에만 적었는데, 그 `error` 는 **나라
데이터가 아직 없을 때만** 화면에 나온다. 그래서 도시 아이템 받기가 실패하면
아무 말 없이 빈 목록이 됐고, 고른 도시가 그대로면 효과가 다시 돌지 않아
스스로 낫지도 않았다. 이제는 화면에 적고 `다시 받기` 를 준다. 나라 데이터
실패 화면에도 `다시 받기` 와 `비우고 새로 받기` 를 붙였다.

## 아이패드 화면 캡처가 알려 준 것

사용자가 보내 준 두 장과 한 줄이 결정적이었다.

- 첫 장: 마드리드는 **선택되어 있고**(주황 테두리 + ✓), 커서는 톨레도 카드
  위에 있는데 눌러도 아무 일이 없다.
- 둘째 장: 스크롤바는 있는데(=문서에 높이가 있다) 화면은 **까맣다.**
- 그리고 — "기존에 선택된 카탈루냐 지방은 선택 취소 및 선택이 동작했어."

계산이 무거운 것부터 지웠다. 1단계 미리보기가 매 렌더마다 도는
`buildItinerary` 는 8곳에 2ms, 도시 쌍 표는 0.1ms 다. 주범이 아니다.

남은 것은 그리기·합성 쪽이고, 거기서 **명백히 잘못 쓴 것 둘**이 나왔다.

### `height: 100%` 는 이 페이지에 맞지 않는다

```css
html, body, #root { height: 100%; }   /* 잘못 */
```

내용이 화면보다 긴 페이지에 이걸 걸면 **body 상자는 화면 높이에 고정되고
내용만 그 밖으로 삐져나간다.** 아이패드 기준으로 body 는 1366px 인데 문서는
7251px 다. 사파리는 이 상태에서 스크롤·합성·히트테스트가 어긋나는 일이
있다 — 손가락은 카드 위에 있는데 눌리지 않고, 스크롤한 자리는 칠해지지 않아
검게 남는 식이다. 증상 셋과 모양이 그대로 겹친다.

`min-height` 로 바꿨다. 이건 취향이 아니라 맞고 틀림의 문제다.
`overscroll-behavior-y: none` 도 걷었다 — 브라우저 스크롤과 다툴 이유가 없다.

### 붙박이 막대의 `backdrop-filter`

머리줄(`sticky`)과 바닥 막대(`fixed`) 둘 다 `backdrop-filter: blur(12px)` 를
걸고 있었다. 붙박이 요소에 이걸 걸면 **페이지 전체를 배경으로 삼는 합성
레이어**가 생긴다. 사파리에서 이 레이어가 다시 칠해지지 않거나 히트테스트를
가로채는 일이 알려져 있다. 장식 하나와 '눌리지 않는 화면' 을 바꿀 수는 없어
불투명 배경으로 되돌렸다.

### 사파리 엔진으로 확인한 것과, 못 한 것

WebKit 을 이 환경에 올려(아래 '사파리로 검증하기') 실제 사파리 엔진으로
돌렸다.

**확인된 것 — `height: 100%` 결함은 진짜다.**

```
수정 전   body 1366px · html 1366px · 문서 4213px    ← body 가 화면 높이에 갇힘
수정 후   body 4212.7px · html 4212.7px · 문서 4213px
```

사파리 엔진이 실제로 그렇게 계산한다. 검증의 `■ 10` 을 수정 전 판에 돌리면
이 검사와 흐림 합성 검사가 **둘 다 실패**하고, 수정 후에는 통과한다.

**확인하지 못한 것 — 눌리지 않는 증상과 검은 화면.**

헤드리스 WebKit 에서는 아이패드 크기·다크 모드·터치 탭으로 같은 흐름을
돌려도 도시가 여섯 개까지 정상으로 선택되고, 길게 스크롤해도 화면이
비지 않는다. 148검사 전부 사파리 엔진에서도 통과한다.

헤드리스 WebKit 은 실기기의 GPU 타일링·합성기 동작까지 흉내 내지는 못한다.
'눌리지 않음' 과 '검은 화면' 은 바로 그 층에서 나는 종류의 증상이라, **이
환경에서 볼 수 없는 것이 당연하다.** 위 둘은 증상과 모양이 겹치고 그 자체로
잘못된 것을 고친 것이지, 재현으로 원인을 못 박은 것이 아니다. 그래서 진단
기록(→ `14-diagnostics.md`)을 함께 두었다.
