# 하루가 밀린 날 — 시간대 버그

## 증상

4월 30일 출발로 넣었는데, 4단계 일정이 **4월 29일**부터 시작했다.
1단계 입력칸에는 분명히 `2026-04-30` 이 그대로 들어 있었다.

## 원인

날짜를 넣을 때와 꺼낼 때 **다른 달력**을 썼다.

```js
function addDays(iso, n) {
  const d = new Date(`${iso}T00:00:00`);   // ← 로컬 자정으로 파싱
  d.setDate(d.getDate() + n);
  return d.toISOString().slice(0, 10);     // ← UTC 기준으로 되돌림
}
```

한국(UTC+9)에서 `2026-04-30T00:00:00` 은 UTC 로 `2026-04-29T15:00:00Z` 다.
`toISOString()` 은 UTC 를 쓰므로 앞의 열 글자는 `2026-04-29` 가 된다.
넣은 날이 그대로 하루 뒤로 밀린 것이다.

같은 실수가 다섯 군데에 있었다.

| 곳 | 하던 일 | 밀리면 생기는 일 |
|---|---|---|
| `planner.ts` `addDays` | 일정의 모든 날짜 | 일정이 하루 앞에서 시작 |
| `lodging.ts` `nextDay` | 체크인·체크아웃 | 숙소 예약 링크가 하루 앞 |
| `store.ts` `defaultState` | 처음 열었을 때 기본 날짜 | 기본값이 30일이 아니라 29일 뒤 |
| `Step1Basics.tsx` `tripDays` | 며칠 여행인가 | 7일 여행이 6일로 |
| `App.tsx` weekday | 요일별 운행 편 거르기 | 하루 전 요일로 기차를 고름 |

`Step1Basics.tsx` 안에서도 `tripDays` 는 로컬(`T00:00:00`)로,
`moveStart`/`moveEnd` 는 UTC(`T00:00:00Z`)로 파싱하고 있었다.
한 파일 안에서 두 달력이 섞여 있었던 셈이다.

## 왜 검사에 안 걸렸나

**검사를 돌리는 컨테이너가 UTC 다.** UTC 에서는 로컬 자정과 UTC 자정이
같은 순간이라 이 버그가 존재하지 않는다. 브라우저 검사 183건이 전부
통과하는 동안 사용자만 겪었다.

한국(+9)만의 문제도 아니었다. 여행지인 **스페인도 여름에는 UTC+2** 라
현지에서 열어도 똑같이 밀렸다.

## 고친 방법

달력 계산을 `lib/caldate.ts` 한 곳으로 모았다. 안에서는 UTC 자정만 쓰고
(UTC 에는 서머타임이 없어 하루가 항상 24시간이다) 밖으로는 `YYYY-MM-DD`
문자열만 오간다. 브라우저 시간대가 무엇이든 결과가 같다.

```ts
export function dayMs(iso)          // 'YYYY-MM-DD' → UTC 자정 epoch
export function msDay(ms)           // epoch → 'YYYY-MM-DD'
export function addDays(iso, n)     // n 일 뒤
export function dayDiff(a, b)       // a 에서 b 까지 며칠
export function weekdayOf(iso)      // 요일 (0 = 일요일)
export function todayISO()          // 오늘 — 브라우저가 보는 달력 그대로
```

`todayISO()` 만 로컬 달력을 읽는다. "오늘" 은 사용자의 오늘이어야 하기
때문이다. 나머지는 전부 시간대와 무관하다.

진단 로그의 시각도 UTC 로 찍고 있었다. 자기 로그를 읽는 사람이 자기
시계와 맞춰 볼 수 있어야 해서 로컬 시각으로 바꿨다.

## 다시 안 나게 한 방법

컨테이너가 UTC 인 한, 시간대를 바꿔 보지 않으면 같은 실수를 또 놓친다.
두 겹으로 막았다.

**1. `scripts/date-check.mjs` — 엔진**

시간대 열 곳(UTC, 한국, 키리바시 +14, 미국 동·서부, 스페인, 네팔 +5:45,
로드하우 +10:30, 채텀 +12:45)에서 **자식 프로세스를 따로 띄워** 같은
계산을 돌리고 답이 전부 같은지 본다. `TZ` 는 프로세스가 뜰 때 한 번만
읽히기 때문에 한 프로세스 안에서는 바꿀 수 없다.

서머타임 경계(스페인 3/29, 미국 3/8, 호주 4/5)와 윤일, 연말을 함께 본다.

**2. `scripts/verify.mjs` ■1-c — 화면**

세 시간대(UTC, 한국, 스페인)에서 창을 새로 열어 4/30~5/6 여행을 실제로
만들고, 4단계 첫 날짜가 4/30 인지 본다. `VERIFY_TZ=Asia/Seoul` 로 검사
전체를 한 시간대에 몰아 돌릴 수도 있다.

두 검사 모두 옛 코드로 되돌려 실패하는 것을 확인했다. 되돌린 판으로
브라우저를 돌리면 한국·스페인에서 `2026-04-29` 가 그대로 다시 나온다.
