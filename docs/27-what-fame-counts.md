# 명성은 무엇을 세고 있었나

`docs/26` 2단계에서 **실패가 전부 `fame<=2` 안에서 일어난다**는 것을
알아냈다. 그러면 그 숫자를 정하는 로직 자체가 옳은지부터 봐야 한다.
스페인 볼거리 1,640곳 전체를 위키데이터에 다시 물어 확인했다.

---

## 먼저, 조회는 제대로 돌고 있다

id 가 있는 1,080곳 중 1,078곳을 다시 받아 그때의 규칙으로 재계산했다.

| | |
|---|---|
| 저장값과 일치 | **1,069곳 (99%)** |
| 어긋남 | 9곳 |
| 리다이렉트로 조회 실패 | **0곳** |
| 위키데이터에서 사라진 항목 | 2곳 |

어긋난 9곳은 대부분 수집 이후 위키백과가 움직인 것이다(테로르 2→5,
데이아 3→5). **조회·캐시·id 매칭에는 고장이 없다.**

---

## 그런데 세는 대상이 주석과 달랐다

`enrich.mjs` 의 주석은 이렇게 적혀 있었다.

> *Popularity proxy: how many **Wikipedia language editions** cover the place.*

`rank.ts` 도 같다 — *"명성: 위키백과 언어판 수"*. 그런데 코드는

```js
const n = Object.keys(ent.sitelinks ?? {}).length;   // 전부 센다
```

위키데이터의 sitelink 에는 위키백과 말고도 **커먼즈·위키보이지·위키인용집·
위키뉴스**가 들어 있다. 실제로 재보니

| | |
|---|---|
| 커먼즈 하나 때문에 정확히 +1 | **917곳 (86%)** |
| 위키보이지 sitelink 를 가진 것 | 52곳 |
| 위키인용집·위키뉴스 | 47곳 |
| **등급이 한 칸 부풀어 있던 것** | **256곳 (24%)** |

부푼 256곳의 내역은 `2→1: 198 · 3→2: 51 · 4→3: 4 · 5→4: 3`.
**198곳은 위키백과 언어판이 2개인데 커먼즈가 얹혀 3으로 세어져 `pop 2`
를 받았다** — 바로 문제의 덩어리 안이다.

위키보이지가 섞이는 것은 특히 나쁘다. **이 앱의 원자료가 위키보이지다.**
자기가 읽은 가이드에 실렸다는 이유로 명성을 한 칸 얹어 주는 셈이다.

### 다만 순위가 좋아지지는 않는다

고쳐도 0-1 성적은 거의 그대로다(상위10% 52% → 52%). 86%에게 붙던 +1 은
사실상 **상수**였고, 상수는 순위를 가르지 못하기 때문이다.
바뀌는 것은 **칸막이의 위치**다 — 기준선 0.45 를 넘는 볼거리가
420곳에서 400곳으로 준다. 그래서 이 고침은 기준선 재실측과 한 몸이다.

---

## 그리고 등급표가 두 개였다

같은 데이터 안에 수집 경로가 둘인데, 표가 서로 달랐다.

| 경로 | 표 |
|---|---|
| `enrich.mjs` — 위키보이지 | `40→5 · 18→4 · 7→3 · 3→2 · 그 아래 **1**` |
| `wdnearby.mjs` — 위키데이터 | `40→5 · 18→4 · 7→3 · **그 외 2**` ← 1 이 없다 |

위키데이터 경로로 들어온 것이 볼거리의 32%(532곳)다. 그쪽은 **언어판이
하나뿐이어도 절대 1 이 되지 않는다.** 지금 셈법으로는 해당하는 것이 5곳뿐
이라 표가 안 났지만, 위키백과판만 세면 3 미만이 135곳으로 늘어 **그만큼이
경로에 따라 갈린다.**

게다가 `wdnearby` 가 쓰던 `wikibase:sitelinks` 는 SPARQL 이 주는 전부
세기 값이라, 위쪽 칸막이도 헐거웠다.

**고쳤다.** 표와 셈법을 `enrich.mjs` 한 곳으로 모으고, `wdnearby` 는
SPARQL 의 sitelinks 를 **싼 1차 거르개로만** 쓰고 등급은 같은 함수로 받는다.
`pipeline/popularity-check.mjs` 가 이 둘이 다시 갈라지는 것을 막는다
(되돌려 확인했다 — 어느 쪽을 되돌려도 걸린다).

## 남은 하나 — '모른다' 가 '안 유명하다' 보다 높다

연결이 없으면 기본값 **2**, 연결이 있고 언어판이 두 개 이하면 **1**.
즉 **찾아본 적 없는 곳이 안 유명하다고 확인된 곳보다 높게 앉는다.**

| | |
|---|---|
| id 가 없어 기본값 2 를 받은 볼거리 | **562곳** |
| id 가 있고 1 을 받은 볼거리 | 58곳 |

0-2 에서 확인한 대로 이 기본값 2 는 후하다 — id 가 없는 것을 좌표로
찾아보면 대개 언어판이 한둘이다.

**다만 순위로는 거의 티가 안 난다.** 기본값을 1 로 내려 재보면
상위10% 49→50% · 하위밀림 19→17% · 평균 22→23%. 오르내림이 섞인다.
그래서 지금 손대지 않았다. 이것은 **기준선을 다시 정할 때 같이 정할 값**이다.

## 이 감사가 26 문서를 하나 고친다

2단계에서 이렇게 적었다.

> *`fame` 을 원값으로 펴도 그것들의 실제 언어판 수는 0~3 이라
> 0 과 0 은 여전히 같다.*

**절반만 맞았다.** 그 말은 연결이 **없는** 562곳에는 맞지만, `pop=2` 인
1,085곳 중 나머지 **523곳은 연결이 있고 언어판이 3·4·5·6 으로 갈린다.**

| pop=2 인 1,085곳 | |
|---|---|
| 언어판 3개 | 208곳 |
| 4개 | 135곳 |
| 5개 | 92곳 |
| 6개 | 82곳 |
| 연결 없음(기본값 2) | 562곳 |

실제로 `fame` 을 원값(로그)으로 바꿔 재면

| | 상위10% | 상위25% | 하위밀림 | 평균 |
|---|---|---|---|---|
| 지금 (5칸 버킷) | 49% | 68% | 19% | 22% |
| **원값 로그** | **52%** | **73%** | **16%** | **21%** |

크지 않지만 진짜 이득이고, `why` 깊이(2단계)와 **재료가 달라 겹치지 않는다.**

못 알아본 대표 28곳을 갈라 보면 왜 이 이득이 이 정도에서 멈추는지 보인다.

| | |
|---|---|
| 연결이 있다(언어판 1~6) | **12곳** ← 원값으로 펴면 닿는다 |
| 연결이 없다 | **16곳** ← 명성 계열로는 닿지 않는다 |

**즉 3단계는 두 재료가 다 필요하다** — 연결된 절반은 원값으로,
연결이 없는 절반은 사람이 쓴 `why` 의 깊이로.

## 고친 것과 안 고친 것

| | |
|---|---|
| **고침** | 위키백과 언어판만 센다 (`wikipediaEditions`) |
| **고침** | 등급표를 한 곳으로 (`popularityOf`) · 두 경로가 같은 함수를 쓴다 |
| **고침** | `popularity-check.mjs` 로 다시 갈라지는 것을 막는다 |
| **뒤이어 고침** | `app/public/data/` 의 값 — `pipeline/repopulate-popularity.mjs` 로 `sitelinks`·`popularity` 두 필드만 다시 썼다(2,142개 중 266개 이동). 3단계에서 기준선을 함께 다시 재면서 반영했다 |
| **뒤이어 고침** | 기본값 — 이제 원값이 `null`(모른다)이고 `fame` 이 `UNKNOWN_FAME` 을 준다. '찾아봤더니 없다'(0)와 구분된다 |

> 3단계(docs/26)에서 이 감사의 결론을 전부 반영했다 — 셈법을 고친 값으로
> 데이터를 다시 쓰고, `fame` 을 등급 대신 원값으로 펴고, 기준선을
> 0.45 → 0.385 로 다시 실측했다.
