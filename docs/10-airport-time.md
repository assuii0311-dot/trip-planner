# 공항 시간과 실제로 쓸 수 있는 날

## 문제

계획이 **달력 날짜만** 세고 있었다. 11일이면 11일치를 짰다.

그런데 첫날 오후 4시에 착륙하면 그날은 저녁 한 끼가 전부이고, 마지막 날
낮 12시 비행기면 아침에 짐을 끌고 공항으로 간다. 실제로 쓸 수 있는 날은
11일이 아니라 9일 남짓인데, 앱은 11일치를 담으라고 했다.

공항은 착륙과 이륙 사이에만 있는 것이 아니다. 입국심사와 수하물, 시내로
들어가는 이동, 돌아갈 때의 체크인과 보안 — 이 시간들이 여행의 앞뒤를
반나절씩 먹는다.

## 입력

1단계에서 공항을 고르면 **도착 시각 / 출발 시각**을 묻는다. 대략이면
된다. 안 넣으면 예전처럼 달력 일수로 짠다.

## 값의 근거

| 항목 | 값 | 근거 |
|---|---|---|
| 입국심사·수하물·세관 | 55분 | 인천 직항 공항(MAD·BCN) — 셍겐 밖에서 바로 입국 |
| 수하물·출구 | 30분 | 그 밖의 공항 — 유럽 어딘가에서 갈아타 심사가 끝나 있다 |
| 짐 풀기 | 30분 | 숙소에 짐을 두고 나오는 시간 |
| 체크인·보안·출국심사 | 180분 | 장거리 국제선 3시간 전 도착 권장 (항공사 공지) |
| 〃 (셍겐 안 단거리) | 120분 | 2시간 |
| 공항 ↔ 시내 | `18분 + km × 1.5` | 아래 참고 |

공항~시내 식은 알려진 값에 맞춰 정했다.

| 공항 | 계산 | 실제 |
|---|---|---|
| 마드리드 MAD | 40분 | 40분 |
| 바르셀로나 BCN | 37분 | 35분 |
| 그라나다 GRX | 42분 | 45분 |
| 빌바오 BIO | 25분 | 25분 |
| 산티아고 SCQ | 34분 | 30분 |
| 팔마 PMI | 30분 | 25분 |

평균 오차 4분이다. 전부 추정치이므로 화면에서 내역을 펼쳐 보여 준다 —
사용자가 자기 항공권을 보고 판단할 수 있어야 한다.

## 계획에 어떻게 쓰이나

- **첫날**은 `착륙 + 입국 절차 + 시내 이동 + 짐 풀기` 뒤에 시작한다.
  16시 착륙이면 18:05부터다. 그 시각 이전 슬롯은 아예 만들지 않는다.
- **마지막 날**은 `이륙 − (도시 간 이동 + 공항 이동 + 체크인)` 에 끝난다.
  그 시각 이후로 넘어가는 일정은 넣지 않는다.
- **'마지막 날 일정' 선택(없음/오전만/종일)** 은 시각을 넣으면 자동으로
  정해진다. 비행기 시각이 정하는 것을 사람에게 고르라고 할 이유가 없다.
- **3단계 예산**이 달력 일수가 아니라 쓸 수 있는 날이 된다.
  "달력은 11일이지만 첫날 입국과 마지막 날 출국에 1.7일이 들어갑니다."

## 마지막 날 있는 도시가 공항 도시와 다를 때

왕복 항공권으로 마드리드에서 나가는 일정이라도 마지막 밤을 세비야에서
보내면, 공항까지는 40분이 아니라 **세비야→마드리드까지 얹은 시간**이다.
예전에는 공항이 속한 도시로만 계산해 비행기를 놓칠 안내를 했다.

```
같은 도시   공항 이동 40분 + 체크인 180분              = 220분
다른 도시   도시 간 이동 197분 + 공항 이동 40분 + 180분 = 417분
            → 12시 비행기면 05:03에는 나서야 한다
```

## 함께 고친 것

- 마지막 날이 비면 "항목이 부족합니다" 라고 했다. 비행기 시각 때문에
  아침에 바로 공항으로 가는 것과 담은 것이 모자란 것은 다른 일이다.
  이제 "공항으로 가는 날입니다. 08:20에는 나서야 해서…" 라고 적는다.
- 테네리페 남부(TFS)가 산타크루스에서 1시간 40분인데 안내가 없었다.
  섬 반대편 끝이라는 사실을 note 에 적었다. TFN·LPA 도 함께.

## 비행시간은 왜 묻지 않는가

계획은 처음부터 끝까지 **스페인 현지 시각**으로 돌아간다. 그리고 항공권에는
양쪽 끝의 현지 시각이 다 찍혀 있다 — "인천 10:30 출발 · 마드리드 17:55 도착".
그러니 현지 착륙·이륙 시각을 그대로 받는 것이 사용자에게 가장 적은 입력이다.

비행시간을 받으면 오히려 일이 는다. 인천 출발 시각 + 비행시간 + 시차 +
날짜변경까지 조합해야 착륙 시각이 나오는데, 그 값은 이미 항공권에 적혀 있다.
사용자에게 항공권을 보고 계산하라고 시키는 셈이다.

다만 비행시간이 **간접적으로** 쓰이는 곳이 하나 있다. 한국에서 스페인으로
오는 길에 짧은 것은 없다 — 직항 14시간, 경유면 16~20시간이다. 그래서
착륙 시각이 들어온 첫날은 무조건 '장거리 비행으로 내린 날' 로 보고
**밤 일정을 넣지 않고 저녁까지만 쓴다.** 예전에는 16시에 내린 날 22시에
라운지 일정이 잡혔는데, 몸으로는 새벽 5시에 술을 마시라는 안내였다.
물어봐야 답이 달라지지 않으므로 묻지 않는다.

## 날짜의 뜻

'출발일 / 도착일' 이었다. 그런데 같은 화면에서 '도착 시각' 은 스페인에
내리는 시각(첫날)이고 '출발 시각' 은 스페인에서 뜨는 시각(마지막 날)이라,
**같은 말이 정반대 날을 가리켰다.**

전부 스페인 기준으로 통일했다.

| 예전 | 지금 | 뜻 |
|---|---|---|
| 출발일 | **스페인 첫날** | 현지에 도착하는 날 |
| 도착일 | **스페인 마지막 날** | 현지에서 떠나는 날 |
| 도착일 일정 | **마지막 날 일정** | 이륙 시각을 넣으면 자동 |
| 도착 시각 | **현지 착륙 시각** | |
| 출발 시각 | **현지 이륙 시각** | |

귀국편은 다음 날 한국에 내리므로, **한국 도착일을 넣으면 하루가 더 잡힌다.**
날짜 칸 아래에 그 사실을 적어 둔다.

## 검증

`app/scripts/airport-check.mjs` — 공항~시내 이동이 실제와 맞는지, 입국·
출국 절차가 구분되는지, 쓸 수 있는 날 계산이 상식적인지, 도시 간 이동이
출국 준비에 더해지는지, 설명 없는 공항이 비상식적으로 멀지 않은지.

`verify.mjs` 는 실제 브라우저에서 첫날 일정이 착륙 뒤에 시작하고 마지막
날 일정이 공항 출발 전에 끝나는지 확인한다.
