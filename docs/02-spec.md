# 2. 기능 정의

5단계 흐름의 각 단계가 무엇을 입력받아 무엇을 내놓는지 정의한다.

## 산출물 형태

**모바일 웹앱(PWA).** React + TypeScript + Vite 로 만들고 정적 파일로 배포한다.

- 아이패드와 폰 브라우저에서 바로 열리고, 홈 화면에 추가하면 앱처럼 전체화면으로 뜬다
- 설치와 심사가 필요 없고, 링크 하나로 동행자와 공유된다
- 서비스 워커가 앱과 도시 데이터를 캐시해서 **현지에서 로밍 없이도 확정 일정을 볼 수 있다**
- 서버·API 키·과금이 없다

저장은 브라우저 `localStorage` 에 하고, JSON 내보내기/가져오기로 기기 간 이동과 공유를 처리한다.

## 1단계 — 기초 정보

| 입력 | 형태 | 쓰이는 곳 |
|---|---|---|
| 가고 싶은 도시 | 60곳 전부에서 다중 선택 | 후보 아이템 범위, 취향 역산 |
| 출발일 · 도착일 | 날짜 두 개 | 일자 계산 |
| 마지막 날 | 없음 / 오전만 / 종일 | 마지막 날 슬롯 수 |
| 인원 | 1~4명+ | 비용 안내 |

### 거점을 먼저 고르게 하지 않는다

스페인을 모르는 사람에게 "거점 도시를 고르세요"는 답할 수 없는 질문이다.
어디가 거점인지 알려면 이미 스페인을 알아야 한다.

그래서 **60개 도시를 권역별로 전부 보여 주고, 무엇이 거점인지는 고른 뒤에 앱이 판단한다.**
각 도시 카드에는 한 줄 성격, 강점 테마, 대표 명소 3곳, "이런 분께 적합" 문구,
사진과 가기 좋은 계절을 넣어 모르는 사람도 고를 수 있게 했다.
처음 스페인에 오는 사람이 놓치기 쉬운 12곳에는 '첫 방문' 배지를 붙였다.

### 거점은 집합 덮개 문제로 푼다

고른 도시를 하나씩 탐욕적으로 묶으면 숙소를 네 번 옮기는 계획이 나온다.
여행자에게 중요한 것은 **숙소를 몇 번 옮기느냐**이므로, 고른 도시를 모두 담되
거점 수를 최소로 하는 집합 덮개로 푼다.

후보에는 **고르지 않은 도시도 넣는다.** 톨레도·세고비아·아빌라만 고른 경우
정답은 '마드리드에 묵기'인데 마드리드는 사용자가 고르지 않았기 때문이다.
밖에서 끌어온 거점에는 '제안' 배지와 이유를 붙인다.

이유 문구에는 **데이터로 확인할 수 있는 것만 쓴다.** 숙소 사정이나 도시 분위기는
가진 데이터로 알 수 없으므로 "숙소가 마땅치 않다" 같은 문장은 넣지 않는다.
숙소를 몇 번 옮기게 되는지, 이동이 몇 분인지만 말한다.

### 당일치기 한계

| 구간 | 한계 | 근거 |
|---|---|---|
| 조사해 둔 51쌍 | 편도 165분 | "실제로 당일치기로 다닌다"는 확인이 있다 |
| 거리 추정 | 편도 110분 | 확인이 없고, 장거리에서 낙관적으로 나온다 |

추정치를 조사값과 같게 두었더니 "마드리드에 묵고 빌바오·세비야를 당일치기"라는
제안이 나왔다. 왕복 4시간짜리 이동이다. 지금은 마드리드~코르도바(추정 110분,
실제 AVE 1시간 45분)는 통과하고 마드리드~세비야(추정 132분, 실제 2시간 30분)는 걸러진다.

간선역이라고 모두 고속철이 다니는 것도 아니다. 빌바오와 산티아고는 지역 간선이지만
마드리드까지 AVE 가 없어, 직통 계수를 쓰는 집합(`AVE_HUBS`)을 따로 두었다.

## 2단계 — 취향 확인 (역산 + 5문항)

취향을 처음부터 캐묻지 않는다. **1단계에서 고른 도시가 이미 취향의 진술이다.**

각 도시에는 8개 테마에 대한 성격 프로필이 손으로 매겨져 있다(0~3).
고른 도시들의 프로필을 평균 내고 0~3으로 펼쳐 테마별 관심도를 역산한다.
2단계에서는 그 결과를 보여 주고 **틀린 것만 고치게 한다.** 손댄 항목에는 '수정함'
표시가 붙고, 되돌리기 버튼이 있다.

역산은 **도시 성격 프로필에서만** 한다. 수집한 아이템 개수에서 역산하지 않는다.
아이템 수는 Wikivoyage 문서가 얼마나 자세한지를 반영할 뿐, 그 도시의 성격이 아니다.

남은 질문은 다섯 개다. 도시 선택으로는 알 수 없는 것만 남겼다.

| # | 항목 | 형태 | 쓰이는 곳 |
|---|---|---|---|
| 1 | 하루 강도 | 1~5 | 하루 활동 수, 체력 상한 |
| 2 | 예산 | 알뜰/보통/넉넉 | 상한 초과분 감점, 무료 가산 |
| 3 | 동행 | 혼자/둘이/친구/아이/부모님 | 고강도 항목 감점 |
| 4 | 음식 취향 | 다중 선택 8종 | 태그 일치당 +9 |
| 5 | 밤 시간 선호 | 0~3 | 나이트라이프 가감점 |

나머지(유명한 곳 ↔ 숨은 곳, 하루 시작 시각, 이동 반경, 사진 중요도)는 접어 두고,
도시 태그에서 기본값을 채운다. 펼쳐서 바꿀 수 있다.

## 3단계 — 테마별 리스트업 (개편 전)

수집한 아이템을 8개 활동 테마로 묶어 보여준다. 선택은 받지 않는다.

`역사·유적` `예술·박물관` `랜드마크·건축` `자연경관` `미식` `나이트라이프` `액티비티` `쇼핑·시장`

테마 분류는 **아이템 이름을 먼저 보고, 그다음 설명을 본다.**
"Cathedral" 은 설명에 그림 이야기가 많아도 역사·유적이지 예술·박물관이 아니기 때문이다.

## 4단계 — 우선순위 선택 (개편 전 — 3단계에 통합됨)

체크박스로 후보에 넣고, 별 1~3개로 순위를 준다.

| 상태 | 의미 | 가중치 |
|---|---|---|
| 체크 해제 | 제외 — 계획에 넣지 않는다 | — |
| ★ | 관심 | 18 |
| ★★ | 가고 싶다 | 40 |
| ★★★ | 꼭 간다 | 75 |

별을 주지 않은 항목도 취향 점수만으로 후보에 남는다. 3개 옵션이 서로 달라 보이려면 여유 후보가 필요하기 때문이다.
`취향대로 추천 담기` 버튼이 상위 항목을 한 번에 담아 첫 선택의 부담을 덜어준다.

여행 일수 × 2 개 이상을 골라야 다음 단계로 넘어간다.

## 5단계 — 계획 3안 (지금은 4단계)

**밀도와 이동량을 기준으로** 세 가지를 만든다. 같은 우선순위에서 출발하므로 비교가 쉽다.

| 옵션 | 하루 활동 수 | 같은 날 묶는 반경 | 밤 일정 |
|---|---|---|---|
| 알찬형 | 3 + 강도/1.5 (최대 6) | 6km | 포함 |
| 균형형 | 2 + 강도/2 (최대 5) | 4km | 포함 |
| 여유형 | 3 고정, 활동 사이 30분 여백 | 2.5km | 없음 |

### 배치 알고리즘

1. 아이템을 점수순으로 정렬한다 (별점 + 취향 + 유명도 + 예산 + 체력 보정)
2. 일수를 거점에 배분하고, 거점에 딸린 근교를 하루씩 배치한다.
   아이템이 20개 미만인 근교는 오전만 다녀오고 오후에 거점으로 돌아온다.
   모든 근교 당일치기는 저녁을 거점에서 먹는다 — 소도시는 저녁 식당이 일찍 닫고
   돌아오는 막차도 있기 때문이다. 복귀 구간은 `[세고비아→마드리드 27분]`으로 표시된다
3. 하루마다 **가장 점수가 높은 비(非)식사 항목을 앵커로 잡고**, 그 반경 안의 항목에 가중치를 준다 — 이동을 억제하는 핵심
4. 오전 → 점심 → 오후 → 저녁 무렵 → 저녁 식사 → 밤 순으로 슬롯을 채운다
5. 점심·저녁 슬롯은 미식 테마만 들어간다. 점심은 12시, 저녁은 19:30, 밤은 21:30 이전으로 당겨지지 않는다
6. 이동 시간은 좌표로 계산한다. 1.2km 이하는 도보(시속 4.5km), 그 이상은 대중교통(시속 18km + 대기 8분)

## 6단계 — 교통 · 예약 안내 (지금은 5단계)

선택한 계획의 각 일정마다 다음을 제공한다.

- **길찾기 딥링크** — 앞 일정에서 다음 일정까지, 대중교통 기준
- **지도에서 열기** — 실시간 영업시간·평점·최근 사진 확인 (저장하지 않는 이유는 `01-data-sourcing.md` 참조)
- **예약 경로** — 공식 홈페이지 / GetYourGuide / Klook, 식당은 TheFork 와 구글 예약 검색
- **근교 이동 안내** — 실제 소요 시간과 수단, Renfe·ALSA·Omio 링크
- **도시별 교통 가이드** — 교통카드 가격, 현지 앱, 주의사항 (정적 데이터)
- **공통 안내** — 식사 시간대, 예매 필수 명소, 휴관일, 소매치기 주의 지역
- **아이템 설명** — 왜 가는가 / 예약·휴관·붐빔·소요·요금 / 주의점
  (형식과 그 근거는 [05-item-descriptions.md](05-item-descriptions.md) 참조)

## 데이터 구조

```
app/public/data/
  spain.json              도시 목록 · 거점/근교 관계 · 교통 가이드
  cities/barcelona.json   해당 도시의 아이템 배열
  cities/girona.json
  ...
```

도시를 추가하려면 `pipeline/registry/<country>.mjs` 에 항목을 넣고 수집 스크립트를 다시 돌리면 된다.
앱 코드는 손대지 않는다.

## 개편 — 6단계에서 5단계로

실제로 계획을 세워 보고 나온 결론: **아이템 목록에서 직접 고를 수가 없다.**
스페인을 모르는 사람 앞에 2천 개를 늘어놓고 "가고 싶은 곳을 고르세요" 라고
한 것이었다. 무엇이 좋은지 모르니 고를 수가 없고, 고르지 못하면 그 뒤 단계가
전부 무의미해진다.

그래서 순서를 뒤집었다. **먼저 코스를 주고, 거기서 빼고 더한다.**

| | 예전 | 지금 |
|---|---|---|
| 1 | 기초 정보 | 기초 정보 (+ 입국·출국 공항) |
| 2 | 취향 | 취향 (그대로) |
| 3 | 아이템 보기 | **도시별 추천 코스** |
| 4 | 우선순위 고르기 | 계획 3안 (+ 일정별 대안) |
| 5 | 계획 3안 | 이동·예약 |
| 6 | 이동·예약 | — |

3·4단계를 합쳤다. 둘 다 같은 목록을 보여 주면서 한쪽은 못 고르고 한쪽은
고르게 하는 구조였는데, 나눌 이유가 없었다.

### 입국·출국 공항 (1단계)

**도시가 아니라 공항 기준이다.** 비행기표를 먼저 끊고 일정을 짜기 때문에,
이미 표를 들고 있는 사람에게 물어야 할 것은 도시가 아니라 공항이다.
처음에는 도시로 받았는데, 도시 선택에 딸린 항목처럼 보여 순서가 뒤바뀌었다.

자리도 **날짜 바로 다음**이다. 처음에는 도시 목록 뒤에 두었는데, 60개 도시
아코디언 때문에 화면 상단에서 3,117px 아래로 밀려 사실상 보이지 않았다.
공항은 도시 선택과 무관하므로 언제나 고를 수 있다.

공항은 `lib/airports.ts` 에 27곳. 인천 직항(MAD·BCN)을 맨 위에 두고 나머지는
경유로 묶었다. 스페인에는 40곳이 넘는 공항이 있지만 국내선 전용이나 연간
이용객이 몇만 명인 곳까지 넣으면 목록만 길어지고 고를 때 방해가 된다.

각 공항에는 서비스하는 도시(slug)를 붙여 두었다. `orderGroups` 는 도시로
동작하므로 공항 → 도시 변환이 필요하다.

**변환 기준은 '실제로 방문하는 도시'다.** 사용자가 고른 도시만 보면 안 된다 —
말라가를 고르지 않았어도 앱이 말라가를 거점으로 제안했다면 AGP 는 말라가
공항이 맞다. 그래서 `assignBases` 결과(제안 거점 포함)를 먼저 계산하고,
거기서 공항 → 도시를 정한 다음 순서를 돌린다. 순환은 없다 — `assignBases`
는 공항을 보지 않는다.

공항 도시가 이번 여행에 아예 없으면(마드리드로 들어와 안달루시아만 도는
경우) 방문 도시 중 가장 가까운 곳으로 붙이고, 몇 km 떨어졌는지 알린다.
150km가 넘으면 "도착 당일 일정은 비워 두세요" 라고 따로 경고한다.

레지스트리에 없는 도시를 쓰는 공항(무르시아·이비사·알메리아)은 가장 가까운
등록 도시에 붙이고 그 사실을 화면에 적는다. 조용히 다른 도시로 바꿔치기하면
사용자가 어긋난 계획을 받는다.

거점 계산은 App 한 곳에서만 한다. 예전에는 1단계 화면이 따로 계산해서,
공항으로 돌린 순서가 화면에 반영되지 않았다.

### 도시별 추천 코스 (3단계)

도시마다 코스 세 가지를 만든다. 기준은 2단계에서 받은 테마 관심도다.

- **고루 보기** — 관심 있다고 한 테마를 몫대로 나눠 담는다
- **○○ 중심** — 한 테마를 늘리고 나머지를 줄인다 (최대 둘)

분량은 그 도시에 배정된 밤 수에 맞춘다. 5일 묵는 도시에는 5일치를 담는다.

**이름이 참인 코스만 내놓는다.** 그 도시에 그 테마 아이템이 몇 개 없으면
두 배로 담으라고 해도 담기지 않는다. 실제로 세비야에서 '역사·유적 중심'을
만들었더니 미식 7 > 역사 6 이 나왔다. 이름을 보고 고르는 화면에서 이름이
거짓이면 고르는 행위 자체가 무의미해지므로, 강조한 테마가 그 코스에서
1위가 되고 균형 코스보다 많을 때만 내놓는다. 조건을 못 채우면 다음 테마로
넘어가고, 그래도 안 되면 코스가 두 개만 나온다.

코스를 바꿔 고르면 **갈아 끼운다**. 더하면 세 코스를 다 눌러 본 사람이
세 코스를 합친 목록을 갖게 된다. 다른 도시의 선택은 건드리지 않는다.

코스 아래에는 그 도시의 전체 아이템이 테마별로 그대로 있다. 코스에서 빼려면
체크를 풀고, 더하려면 아래에서 체크한다.

### 예상 소요 일수

담을 때마다 `N곳 선택 · 예상 M일` 이 갱신된다. 여행 일수를 넘으면 넘는
만큼을 알려 준다. 이게 없으면 20일치를 담아 놓고 7일 일정에서 잘려 나가는
것을 마지막에야 알게 된다.

계산은 `capacity.ts` — 아침 시작 시각과 속도 취향으로 하루 활동 시간을
정하고, 아이템마다 머무는 시간에 이동·대기 18분을 얹어 나눈다.

### 일정별 대안 (4단계)

계획을 보여 주고 "이대로 하세요" 로 끝내면, 마음에 안 드는 한 곳 때문에
앞 단계로 돌아가 처음부터 다시 고르게 된다. 그래서 자리마다 대안을 최대
3개까지 옆에 놓고, 누르면 그 자리에서 바꾼다.

대안은 한 곳일 수도 있고 **두세 곳 묶음**일 수도 있다. 두 시간짜리 미술관
하나를 뺀 자리에는 40분짜리 세 곳이 들어갈 수 있기 때문이다.

**하루 단위로 뽑는다.** 자리마다 따로 뽑으면 점수 높은 몇 곳이 그날 모든
자리에 똑같이 걸린다. 세 자리에 같은 세 곳이 걸려 있으면 고를 것이 없는
것과 같고, 하나를 넣는 순간 나머지 자리의 그 대안은 이미 계획에 들어간
곳이 된다. 앞 자리에서 쓴 것은 뒤 자리에서 뺀다.

넓은 화면(720px 이상)에서는 일정 오른쪽 칸에 붙고, 폰에서는 아래로
내려온다. 390px 에서 오른쪽에 칸을 더 두면 일정 제목이 두 글자씩 끊긴다.

### 예전 저장분

v1 은 6단계였다. `migrate` 가 6단계에 있던 사람을 5단계로 당기고, 고른
아이템과 취향은 그대로 쓴다. 2천 개에서 골라낸 것을 구조가 바뀌었다는
이유로 날리지 않는다.

## 중간 저장

아이템이 2천 개가 넘는다. 4단계에서 고르는 일을 한 번에 끝내라고 요구할 수
없으므로, 며칠에 걸쳐 나눠 하는 것을 전제로 잡았다.

### 무엇이 저장되는가

상태가 바뀔 때마다 `localStorage` 에 통째로 넣는다(`store.ts`). 여기에는
고른 아이템과 별점뿐 아니라 **보던 자리**도 들어간다 — 몇 단계였는지,
4단계에서 어느 테마를 펼쳐 두었는지, '고른 것만 보기' 를 켜 두었는지.

보던 자리를 저장하지 않으면 다시 들어올 때마다 첫 테마로 튕겨 나가고, 8개
테마 중 어디까지 봤는지 사용자가 기억해 내야 한다. 그건 저장이 안 된 것과
크게 다르지 않다.

### 저장됐다는 사실을 보여준다

자동 저장은 예전에도 돌고 있었지만 화면에 아무 표시가 없었다. 그러면 앱을
닫아도 되는지 알 수 없어 결국 한 번에 끝내려 하게 된다. 상단 단계 표시줄에
`저장됨 · 방금` 을 넣었고, 1분마다 `3분 전` → `1시간 전` 으로 바뀐다.

**저장 실패를 삼키지 않는다.** 사파리 프라이빗 모드나 저장 공간 부족이면
`saveState` 가 실패하는데, 예전에는 조용히 넘어갔다. 지금은 같은 자리에
`⚠ 저장 안 됨` 이 뜬다. 다 저장된 줄 알고 닫는 것이 최악이다.

### 이어서 하기

복원 자체는 예전에도 됐지만 아무 말이 없어서, 자기가 뭘 하던 중이었는지
화면을 뒤져 알아내야 했다. 무엇이 어디까지 복원됐는지 한 줄로 알린다.

> 이어서 하고 계십니다 · 3시간 전 저장
> 4단계 · 우선순위 · 도시 2곳 · 아이템 23개 선택

막지 않는다 — 앱은 이미 이어서 하는 상태고, 배너일 뿐이다. 같은 자리에
'새로 시작' 을 둬서 아닐 때 빠져나갈 길을 준다.

### iOS 7일 문제

iOS 사파리는 **홈 화면에 추가하지 않은** 사이트의 저장분을 마지막 방문에서
7일이 지나면 지운다(ITP). 며칠에 걸쳐 나눠 고를 계획이라면 실제로 일어나는
일이고, 아무 예고 없이 일어난다.

그래서 홈 화면 앱이 아닌 상태에서 **아이템을 5개 이상 고른 시점에** 한 번
알린다. 5개는 '이제 잃을 것이 생겼다' 는 선이다. 4단계에 들어서자마자 띄우면
아직 아무것도 안 고른 사람에게는 방해일 뿐이다.

홈 화면 앱 여부는 `display-mode: standalone` 과 `navigator.standalone` 으로
판단한다. 홈 화면에 추가한 사람에게는 뜨지 않는다.

경고 안에서 바로 백업 파일을 받을 수 있다. 파일 내보내기·가져오기는 원래부터
있었고, 기기 간 이동과 동행자 공유에도 쓴다.

## 구글 내 지도로 내보내기

고른 장소를 구글 지도에 담아 가고 싶다는 요구.

### 자동 저장은 불가능하다

구글은 바깥에서 지도에 장소를 써넣는 길을 열어 두지 않았다.

- 구글 '내 지도(My Maps)' — 쓰기 API 없음. 예전 Maps Data API 는 폐기됐다
- 구글 지도의 '저장한 장소' 목록 — 쓰기 API 없음
- Places API — 장소를 읽는 API지 사용자 목록에 쓰는 API가 아니다

공식으로 지원되는 유일한 경로가 **파일 가져오기**다. 그래서 한 번에 통째로
넣을 수 있는 KML 을 만들어 주고, 어느 지도에 넣을지는 가져오기 화면에서
사용자가 정한다. "내가 지정하는 지도"라는 요구는 이 방식으로도 지켜진다.

### 두 가지 범위

| | 담기는 것 | 레이어 |
|---|---|---|
| ① 전체 장소 | 고른 도시의 아이템 전부 | 도시별 |
| ② 여행 경로만 | 선택한 계획에 들어간 것 | 일자별 |

현지에서는 ②를 켜 두고 그날 레이어만 보는 쪽이 쓸모 있다.
열흘이 넘으면 레이어 상한(10)에 걸리므로 도시별로 되돌린다.

### 구글이 문서로 밝힌 제한

- 레이어 하나에 2,000개까지 — **넘으면 조용히 잘린다**
- 지도 하나에 레이어 10개
- 지도 하나에 총 10,000개
- KML 5MB

조용히 잘리는 것이 가장 나쁘므로, 넘길 것 같으면 내보낼 때 경고한다.
KML 의 `<Folder>` 하나가 '내 지도' 의 레이어 하나가 된다.

### 좌표가 없는 장소는 뺀다

아이템 2,132개 중 좌표가 있는 것은 1,865개(87.5%)다. 나머지는 지도에 찍을
자리가 없다. 도시 중심에 몰아 찍으면 엉뚱한 자리를 알려 주는 셈이므로 빼고,
몇 곳을 뺐는지 화면에 알린다. 대부분 정해진 자리가 없는 식당·체험이다.

### 파일 이름은 반드시 ASCII

`<a download>` 에 한글이 들어가면 브라우저가 이름을 **통째로 버리고**
`download` 로 저장한다. 확장자까지 사라져서 구글이 KML 로 알아보지 못하고
가져오기가 실패한다. 실제로 확인한 동작이라 `spain-2026-09-29-all.kml`
처럼 ASCII 로 만든다. 지도 안에 보이는 이름은 한글 그대로 둔다 —
그건 KML 내용이라 제한이 없다.

스모크 테스트가 확장자와 KML 네임스페이스, 구글 제한을 매번 검사한다.

### 라이선스

내보내는 것은 우리 데이터(Wikivoyage·Wikidata·OSM 에서 온 이름과 좌표에
직접 쓴 한국어 설명)이지 구글에서 가져온 것이 아니다. 구글 지도 약관이
금지하는 '구글 데이터의 저장·재배포' 에 해당하지 않는다. KML 문서 설명에
출처를 적어 CC BY-SA 표기 의무를 지킨다.
