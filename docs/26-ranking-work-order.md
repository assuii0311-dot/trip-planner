# 순위 엔진 — 작업 순서

`docs/25` 의 분석에서 나온 순서다. **위에서부터 한다.** 아래 것을 먼저 하면
검증할 수단 없이 튜닝하게 되거나, 입력이 틀린 채로 점수만 다듬게 된다.

---

## 0단계 — 재는 것부터 (아직 안 됨)

### 0-1. 회귀 검사를 먼저 만든다 · `scripts/rank-truth.mjs` — **완료**

**이것이 없으면 이후 모든 작업을 검증할 수 없다.**

정답지는 이미 있다 — 도시 등록부의 `highlights`(58개 도시 150곳).
`must` 항이 그것으로 만들어졌으므로 **`must` 를 빼고** 재야 순환이 아니다.

지금 값(기준선으로 삼는다):

| | 지금 |
|---|---|
| 평균 백분위 | 22% (무작위 50%) |
| 상위 10% 안 | 49% |
| 상위 25% 안 | 68% |
| 하위 절반으로 밀림 | 19% (28곳) |

검사는 이 수치가 **나빠지면 실패**한다(여유 2%p). 이후 단계는 전부 이 검사로
판정한다. 엔진이나 데이터를 고쳐 성적이 좋아지면 `BASE` 도 함께 올린다.

되돌려 확인한 결과, 이 검사는 `fame` 을 상수로 두거나(49→32%) 가중을 잘못
바꾸거나(0.40→0.05, 49→45%) 순서를 뒤집으면(49→13%) 걸린다. 반대로
`purpose`·`named`·`guide` 를 없애도 반응하지 않는데, **그 셋이 순위를 거의
가르지 못하기 때문이다**(따로 잰 편차: `purpose` 0.046, `named` 92% 보유,
`guide` 는 대표든 아니든 80% 가 위키보이지). 검사가 무딘 것이 아니라
그 항들이 기여하지 않는다는 뜻이다.

> 이 저장소의 규칙 — 새 검사를 넣었으면 고친 것을 되돌려 실제로 걸리는지
> 확인한다. 안 걸리는 검사는 검사가 아니다.

### 0-2. 연결 실패 규모를 정확히 잰다 — **완료 · 1단계는 값어치가 없다**

**앞서 한 표본 측정(28곳 중 100% 없음)은 틀렸다.** 위키데이터 API 는
정상이었고 개별로 찾으면 나온다. 규모 추정에 쓸 수 없다.

다시 재야 할 것 — 위키데이터 id 가 없는 볼거리(전체의 49%) 가운데

- 찾으면 나오는데 못 찾은 것 (**연결 실패** — 고칠 수 있다)
- 정말 위키데이터에 없는 것 (**구조적** — 다른 방법이 필요하다)

확인된 연결 실패 예: 살라망카 대학 **66개 언어판인데 `pop=2`**,
산타 마리아 델 나랑코(유네스코) 31개 → 2, 마스팔로마스 모래언덕 15개 → 2.

이 비율이 1단계를 할 값어치를 정한다.

#### 잰 결과 — 고칠 것이 거의 없다

먼저 모집단. 볼거리 1,640곳 중 위키데이터 id 가 없는 것은 **560곳(34%)**
이고 **전부 위키보이지 출처**다. 위키보이지 항목의 id 는 편집자가 목록
템플릿에 `wikidata=` 를 적어 뒀을 때만 붙는다 — 앱이 따로 찾지 않는다.
그중 좌표가 있어 찾아볼 수 있는 것이 432곳.

**① id 가 없는 것을 좌표로 찾아봤다** (표본 59곳, 반경 250m SPARQL)

| | |
|---|---|
| 이름이 맞는 항목을 찾음 | 15곳 (25%) |
| **그중 `pop` 이 오르는 것** | **4곳 (7%)** |
| 근처에 다른 것만 있음 | 27곳 (46%) |
| 위키데이터에 정말 없음 | 17곳 (29%) |

찾은 15곳 중에도 대부분은 `pop` 이 **내려간다** — 라 테르미카 언어판 1개,
엘 핌피 2개. **기본값 2 가 실제보다 후했던 것이다.** 위키보이지 편집자가
`wikidata=` 를 안 적은 항목은 대체로 정말 안 유명하다.

**② id 가 있는데 `pop=2` 인 것을 확인했다** (표본 30곳)

| | |
|---|---|
| 지금 값이 맞음 | 29곳 (97%) |
| 과소평가 | **0곳** |
| 과대평가 | 1곳 |

**조회 실패는 없다.** `popularity` 부여 자체는 제대로 돌고 있다.

**③ 살라망카 대학은 연결 실패가 아니었다**

`wikidata=Q5839387` 이 붙어 있고 그것은 "Escuelas Mayores de Salamanca"
(그 유명한 파사드와 개구리가 있는 역사 건물)로 언어판 3개다. 내가 앞서
비교한 Q308963(언어판 66)은 **대학이라는 기관**이다.

여행자가 가는 것은 건물이므로 **연결은 오히려 맞다.** 다만 사람이 방문하는
대상(건물)이 그것이 속한 기관보다 언어판이 훨씬 적다. 이것은 연결 문제가
아니라 **`fame` 이 무엇을 재는지의 문제**다 — 2단계로 넘어간다.

#### 그래서 1단계는 건너뛴다

연결을 고쳐 봐야 560곳 중 7% 안팎(전체 볼거리의 2%)만 오르고, 그나마
내려가는 것이 더 많다. **입력은 대체로 정직하다.** 문제는 그 정직한 입력이
재는 것(세계적 백과사전 명성)이 우리가 알고 싶은 것(여행 가치)과 다르다는
데 있다.

`nameEn` 이 `"Cathedral"`·`"Forum"` 인 것들은 그대로 두어도 대부분 이미
연결돼 있다(세비야 pop 5, 톨레도 pop 5). 산탄데르 대성당처럼 빠진 것은
있지만 소수다.

## ~~1단계 — 입력 고치기 (연결)~~ · **0-2 에서 값어치가 없다고 판명, 건너뜀**

원래 가설은 '입력이 틀렸다' 였다. 재보니 아니었다 — 연결을 고쳐도 전체
볼거리의 2% 남짓만 오르고 내려가는 것이 더 많다. `popularity` 부여도
제대로 돌고 있다(id 가 있는 것 중 조회 실패 0%).

아래는 남겨 두되, **급하지 않은 것으로 내린다.**

### 1-1. 위키데이터 재연결 · `pipeline/`

지금 실패하는 이유로 확인된 것:

- `nameEn` 이 조회 불가능한 일반명사 — 세비야·톨레도·아빌라·산탄데르
  대성당이 모두 `"Cathedral"`, 로마 포룸 박물관이 `"Forum"`.
  (대부분은 다른 경로로 연결됐고 산탄데르만 실패했다)
- 이름만으로 찾다 실패

붙일 수단: 도시명을 붙여 재조회, 좌표 기반 조회, 위키보이지 문서의
위키데이터 링크.

**판정**: 0-1 검사에서 밀린 28곳이 줄어야 한다.

### 1-2. 수집 쓰레기 (작음, 선택)

볼거리에 리들·메르카도나·카르푸·엘 코르테 잉글레스·자라·쇼핑센터가
섞여 있다. **다만 대부분 0.400 이라 기준선이 막고 있어** 코스에는 안
들어간다. 급하지 않다.

## 2단계 — `fame` 의 맹점: '무료로 열려 있는 공간'

밀린 28곳의 정체는 산책로·성벽·전망대·해변·모래언덕·곶·시장이다.
**이름 붙은 건물이 아니라 공간**이고, 위키백과가 독립 항목으로 잘 만들지
않는 종류다.

이것은 **설계자가 이미 한 번 만났던 실패**다. `vetted` 주석:

> *무료로 열려 있는 공간은 영업시간도 요금도 공식 홈페이지도 없다.
> 대표 210곳 중 88곳이 그런 이유로 깎였고, 알함브라가 60위까지 밀렸다.*

`vetted` 에서는 '있으면 가산, 없다고 벌하지 않음' 으로 고쳤다.
**같은 처방을 `fame` 에 적용할 수 있는지**가 이 단계의 질문이다.

1단계를 끝낸 뒤에 남는 것이 진짜 이 문제다 — 지금 28곳 중 일부는
연결 실패일 뿐이므로, 순서를 지켜야 무엇이 진짜인지 알 수 있다.

**판정**: 0-1 검사. 그리고 `RANK_FLOOR` 주석의 보정표(마드리드 10.9일 ·
세비야 3.3 · 톨레도 2.2 · 세고비아 0.9 · 론다 0.5 · 네르하 0.4)가
크게 흔들리지 않아야 한다.

## 3단계 — 점수를 연속값으로 (= 앞서 정한 (나)안)

지금 점수는 계단이다. `fame` 5가지 × `must` 2가지 × `vetted` 3가지 라
**1,640곳이 열 몇 개 값에 뭉쳐 있다.**

```
0.40 → 520곳 ✗   ← 기준선 0.45 바로 아래
0.31 → 411곳 ✗
0.50 → 159곳 ✓
```

기준선을 0.05 만 움직여도 520곳이 한꺼번에 넘어와 조절이 안 된다
(재봤을 때 론다가 0.5일 → 4.0일로 튀었다).

할 것: `fame` 을 버킷 대신 원값으로(언어판 수, 또는 조회수),
`vetted` 를 실제 변별하는 것으로. 지금 `vetted` 세 조각 중 둘은 상수다
(`named` 92% · `anyInfo` 89% 보유, 실질적으로 `guide` 하나).

**왜 3순위인가**: 계단을 없애도 **순서가 옳아지지는 않는다.** 경계의
임의성만 줄어든다. 1·2단계로 순서를 먼저 바로잡아야 뜻이 있다.

**조회수를 쓴다면 주의**: 제목을 위키데이터 sitelink 에서 정확히 받아야
한다. 추측하면 유명한 곳이 0회로 읽혀 거꾸로 강등된다(실제로 겪었다).

---

## 4단계 — 문턱 조정 (= 앞서 정한 (가)안)

1~3단계 뒤에도 남는 것을 손본다.

- **로그로뇨형** (520곳 · 29개 도시): 위키보이지 출처인데 `pop=2` 라
  0.400 에 몰림. 상위 K 보장 등
- **산세바스티안형** (96곳 · 6개 도시): `pop≥3` 인데 위키보이지가 아니라
  `guide` 0.3 을 못 받아 0.410

**사용자 눈에 보이는 유일한 명백한 고장**은 로그로뇨다 — 데이터 37곳이
있는데 **3단계 추천 코스가 아예 안 뜬다.** 1~3단계가 이것까지 고치면
4단계는 필요 없을 수도 있다. **그때 다시 재고 정한다.**

## 이 순서의 근거

| 단계 | 왜 이 자리인가 |
|---|---|
| 0 | 검증 수단이 없으면 나머지가 다 추측이 된다 |
| 1 | 입력이 틀리면 어떤 점수 설계도 소용없다 |
| 2 | 1을 끝내야 남은 것이 진짜 설계 문제인지 알 수 있다 |
| 3 | 순서를 바로잡은 뒤에야 경계를 다듬을 뜻이 있다 |
| 4 | 앞이 다 되면 필요 없을 수도 있다 |
