`docs/25` 의 분석에서 나온 순서다. **위에서부터 한다.** 아래 것을 먼저 하면
검증할 수단 없이 튜닝하게 되거나, 입력이 틀린 채로 점수만 다듬게 된다.

## 0단계 — 재는 것부터 — **완료**

### 0-1. 회귀 검사를 먼저 만든다 · `scripts/rank-truth.mjs` — **완료**

**이것이 없으면 이후 모든 작업을 검증할 수 없다.**

정답지는 이미 있다 — 도시 등록부의 `highlights`(58개 도시 150곳).
`must` 항이 그것으로 만들어졌으므로 **`must` 를 빼고** 재야 순환이 아니다.

지금 값(기준선으로 삼는다):

| | 지금 |
|---|---|
| 평균 백분위 | 22% (무작위 50%) |
| 상위 10% 안 | 49% |
| 상위 25% 안 | 68% |
| 하위 절반으로 밀림 | 19% (28곳) |

검사는 이 수치가 **나빠지면 실패**한다(여유 2%p). 이후 단계는 전부 이 검사로
판정한다. 엔진이나 데이터를 고쳐 성적이 좋아지면 `BASE` 도 함께 올린다.

되돌려 확인한 결과, 이 검사는 `fame` 을 상수로 두거나(49→32%) 가중을 잘못
바꾸거나(0.40→0.05, 49→45%) 순서를 뒤집으면(49→13%) 걸린다. 반대로
`purpose`·`named`·`guide` 를 없애도 반응하지 않는데, **그 셋이 순위를 거의
가르지 못하기 때문이다**(따로 잰 편차: `purpose` 0.046, `named` 92% 보유,
`guide` 는 대표든 아니든 80% 가 위키보이지). 검사가 무딘 것이 아니라
그 항들이 기여하지 않는다는 뜻이다.

> 이 저장소의 규칙 — 새 검사를 넣었으면 고친 것을 되돌려 실제로 걸리는지
> 확인한다. 안 걸리는 검사는 검사가 아니다.

### 0-2. 연결 실패 규모를 정확히 잰다 — **완료 · 1단계는 값어치가 없다**

**앞서 한 표본 측정(28곳 중 100% 없음)은 틀렸다.** 위키데이터 API 는
정상이었고 개별로 찾으면 나온다. 규모 추정에 쓸 수 없다.

다시 재야 할 것 — 위키데이터 id 가 없는 볼거리(전체의 49%) 가운데

- 찾으면 나오는데 못 찾은 것 (**연결 실패** — 고칠 수 있다)
- 정말 위키데이터에 없는 것 (**구조적** — 다른 방법이 필요하다)

확인된 연결 실패 예: 살라망카 대학 **66개 언어판인데 `pop=2`**,
산타 마리아 델 나랑코(유네스코) 31개 → 2, 마스팔로마스 모래언덕 15개 → 2.

이 비율이 1단계를 할 값어치를 정한다.

#### 잰 결과 — 고칠 것이 거의 없다

먼저 모집단. 볼거리 1,640곳 중 위키데이터 id 가 없는 것은 **560곳(34%)**
이고 **전부 위키보이지 출처**다. 위키보이지 항목의 id 는 편집자가 목록
템플릿에 `wikidata=` 를 적어 뒀을 때만 붙는다 — 앱이 따로 찾지 않는다.
그중 좌표가 있어 찾아볼 수 있는 것이 432곳.

**① id 가 없는 것을 좌표로 찾아봤다** (표본 59곳, 반경 250m SPARQL)

| | |
|---|---|
| 이름이 맞는 항목을 찾음 | 15곳 (25%) |
| **그중 `pop` 이 오르는 것** | **4곳 (7%)** |
| 근처에 다른 것만 있음 | 27곳 (46%) |
| 위키데이터에 정말 없음 | 17곳 (29%) |

찾은 15곳 중에도 대부분은 `pop` 이 **내려간다** — 라 테르미카 언어판 1개,
엘 핌피 2개. **기본값 2 가 실제보다 후했던 것이다.** 위키보이지 편집자가
`wikidata=` 를 안 적은 항목은 대체로 정말 안 유명하다.

**② id 가 있는데 `pop=2` 인 것을 확인했다** (표본 30곳)

| | |
|---|---|
| 지금 값이 맞음 | 29곳 (97%) |
| 과소평가 | **0곳** |
| 과대평가 | 1곳 |

**조회 실패는 없다.** `popularity` 부여 자체는 제대로 돌고 있다.

**③ 살라망카 대학은 연결 실패가 아니었다**

`wikidata=Q5839387` 이 붙어 있고 그것은 "Escuelas Mayores de Salamanca"
(그 유명한 파사드와 개구리가 있는 역사 건물)로 언어판 3개다. 내가 앞서
비교한 Q308963(언어판 66)은 **대학이라는 기관**이다.

여행자가 가는 것은 건물이므로 **연결은 오히려 맞다.** 다만 사람이 방문하는
대상(건물)이 그것이 속한 기관보다 언어판이 훨씬 적다. 이것은 연결 문제가
아니라 **`fame` 이 무엇을 재는지의 문제**다 — 2단계로 넘어간다.

#### 그래서 1단계는 건너뛴다

연결을 고쳐 봐야 560곳 중 7% 안팎(전체 볼거리의 2%)만 오르고, 그나마
내려가는 것이 더 많다. **입력은 대체로 정직하다.** 문제는 그 정직한 입력이
재는 것(세계적 백과사전 명성)이 우리가 알고 싶은 것(여행 가치)과 다르다는
데 있다.

`nameEn` 이 `"Cathedral"`·`"Forum"` 인 것들은 그대로 두어도 대부분 이미
연결돼 있다(세비야 pop 5, 톨레도 pop 5). 산탄데르 대성당처럼 빠진 것은
있지만 소수다.

## 2단계 — `fame` 의 맹점 — **완료 · 가설 기각**

### 물었던 것

밀린 28곳의 정체가 산책로·성벽·전망대·해변·모래언덕이라, **위키백과가
독립 항목으로 잘 만들지 않는 '무료로 열려 있는 공간' 을 `fame` 이
깎는다**고 의심했다. `vetted` 에서 똑같은 실패를 이미 한 번 고쳤으므로
(*있으면 가산, 없다고 벌하지 않음*) 같은 처방을 `fame` 에 옮길 수
있는지가 질문이었다.

### 답 — 아니다. 세 번 재서 세 번 다 아니었다

**① 열린 공간은 홀대받고 있지 않다.** 사전 규칙(실내 아님 · 영업시간
없음 · 요금 없음/0)으로 가르면

| | 열린 공간 비율 |
|---|---|
| 전체 볼거리 1,640곳 | 570곳 (35%) |
| 사람이 꼽은 대표 150곳 | 56곳 (37%) |

정답지에서 오히려 **살짝 많다.** 그리고 전체 평균 `popularity` 는
열린 공간 2.40 · 그 밖 2.41 로 **사실상 같다.**

**② 못 알아본 28곳에 열린 공간이 많아 보이는 것은 착시다.**
54%(28곳 중 15) 대 34%(알아본 122곳 중 41) 로 확실히 몰려 있긴 하다.
그런데 명성이 같은 것끼리(`pop<=2` 인 대표 62곳) 갈라 보면

| | 못 알아봄 |
|---|---|
| 열린 공간 30곳 | 15곳 (50%) |
| 그 밖 32곳 | 13곳 (41%) |

**차이가 없다.** 열린 공간이 많아 보인 것은 그것들이 `pop<=2` 에 몰려
있기 때문이지, 열린 공간이라서 밀린 것이 아니다.

**③ 보정을 걸어 봤더니 성적이 내려갔다.** 0-1 검사로 셋 다 재봤다.

| | 상위10% | 상위25% | 하위밀림 |
|---|---|---|---|
| 지금 그대로 | 49% | 68% | 19% |
| 열린 공간 `fame` 바닥 0.50 | **45%** | 67% | 18% |
| 열린 공간 `fame` +0.25 | 48% | 67% | 17% |
| 열린 공간만 `fame` 가중 절반 | **46%** | 66% | 17% |

### `vetted` 의 처방이 옮겨지지 않는 이유

`vetted` 는 **없는 것을 벌하고 있었다** — 영업시간·요금·홈페이지가
없는 것을 결격으로 셌다. 그래서 '있으면 가산' 으로 바꿀 자리가 있었다.

`fame` 은 벌하지 않는다. 위키데이터가 없으면 기본값 2 를 주는데,
0-2 에서 재보니 **그 2 는 오히려 후한 값이었다.** 벌이 없으니 풀 벌이
없다. `fame` 의 문제는 벌이 아니라 **말이 없는 것**이다.

### 진짜 고장은 다른 곳이다 — `fame` 은 아래쪽에서 침묵한다

대표 150곳을 명성 구간으로 갈랐다.

| | 대표 | 못 알아봄 |
|---|---|---|
| `pop` 5 | 18곳 | **0곳** |
| `pop` 4 | 32곳 | **0곳** |
| `pop` 3 | 38곳 | **0곳** |
| `pop` 2 | 60곳 | 26곳 (43%) |
| `pop` 1 | 2곳 | 2곳 (100%) |

**`fame>=3` 이면 한 곳도 안 놓친다. 실패는 전부 `fame<=2` 안에서
일어난다.** 그 덩어리에 볼거리 1,137곳(69%)이 들어 있고, 안에서
`fame` 은 값이 하나뿐이라 순위를 전혀 가르지 못한다. 남은 `vetted` 는
92%·89% 가 갖고 있는 상수라 역시 못 가른다. **동전 던지기가 된다.**

이 표와 열린 공간 반증은 `rank-truth.mjs` 진단에 박아 뒀다 —
같은 가설을 다시 세우지 않기 위해서다.

### 그 덩어리를 가를 수 있는 신호를 찾았다 — 사람이 쓴 `why` 의 길이

`pop<=2` 인 1,137곳 안에서 대표 62곳을 가려내는 신호를 하나씩 쟀다
(배율 1.0 = 정보 없음).

| 신호 | 배율 |
|---|---|
| **`why` 60자 이상** | **15.7** (9.4% ↔ 0.6%) |
| 파일 앞 20% 안 | 3.3 |
| 위키보이지 출처 | 3.0 |
| nameLocal 있음 | 2.2 |
| 요금 정보 있음 | 1.9 |
| 사진 있음 | 1.2 |
| 위키데이터 있음 | 1.2 |

`why` 는 `pipeline/ko/` 에 사람이 손으로 쓴 한 줄이다. 짧은 것들을
읽어 보면 글자 수가 아니라 **판정**이 담겨 있다 — *"지나며 보는 정도"*,
*"남은 것이 많지 않아"*, *"규모는 작습니다"*. 쓴 사람이 이미 등급을
매겨 놓은 셈이다.

0-1 검사로 재면 효과가 크다.

| | 상위10% | 상위25% | 하위밀림 | 평균백분위 |
|---|---|---|---|---|
| 지금 | 49% | 68% | 19% | 22% |
| `vetted` 의 상수 둘을 깊이로 교체 | **57%** | **81%** | **3%** | **14%** |

도시를 번갈아 둘로 갈라도 양쪽이 같이 좋아진다(A 60/15 · B 54/13).

### 다만 이 신호는 아직 설치하지 않는다 — 두 가지 때문에

**첫째, 정답지와 같은 손이 썼다.** `why` 도 `highlights` 도 사람이 쓴
것이라 0-1 검사가 이 신호를 공정하게 재지 못한다. 그래서 **정답지를
바꿔** 따로 쟀다 — 위키데이터 언어판 수(`pop>=4`, 173곳)를 정답으로
두고 점수에서 `fame` 을 아예 뺀 채로.

| | 상위25% | 평균백분위 |
|---|---|---|
| 지금 `vetted` | 44% | 37% |
| 깊이로 바꾼 `vetted` | 48% | 36% |

**딴 손이 만든 잣대로도 나아지긴 한다. 그러나 49→57 만큼은 아니다.**
0-1 에서 보이는 이득의 상당 부분은 같은 손에서 온 거품이다. 설치할
때 이 점을 그대로 적어야 한다.

**둘째, 점수 눈금이 통째로 움직인다.** `vetted` 의 상수 0.7 을 빼면
거의 모든 항목의 점수가 내려가, 기준선 0.45 에서 도시 값어치가

> 마드리드 10.9 → 7.1 · 빌바오 3.5 → **1.1** · 그라나다 3.0 → 1.9

빌바오가 그라나다 아래로 내려간다. 기준선을 0.50·0.55·0.60 으로 올려
봐도 사람의 감각에 맞는 모양이 돌아오지 않는다.
**즉 이것은 기준선 재산정과 한 몸이다 — 3·4단계에서 함께 한다.**

### 2단계 결론

`rank.ts` 는 고치지 않는다. 남긴 것은 (1) 기각된 가설의 묘비와 명성
구간 표를 `rank-truth.mjs` 진단에, (2) 3단계에 넘길 구체적 지시다.

## 3단계 — 점수를 연속값으로 · 4단계와 함께 — **완료**

지금 점수는 계단이었다. `fame` 5가지 × `must` 2가지 × `vetted` 3가지 라
**1,640곳이 25개 값에 뭉쳐 있었다.**

```
0.40 → 520곳 ✗   ← 기준선 0.45 바로 아래
0.31 → 411곳 ✗
0.50 → 159곳 ✓
```

기준선을 0.05 만 움직여도 520곳이 한꺼번에 넘어와 조절이 안 됐다
(재봤을 때 론다가 0.5일 → 4.0일로 튀었다).

### 한 것 — 다섯 가지

**① 데이터에 언어판 원값을 넣었다.** `pipeline/repopulate-popularity.mjs`
가 이미 고른 장소는 그대로 두고 `sitelinks`·`popularity` 두 필드만 다시
쓴다. `collect.mjs` 를 통째로 다시 돌리지 않은 이유는, 넓은 반경 보강이
캐시되지 않아 **돌릴 때마다 장소 선정이 달라지기 때문**이다. 순위를
고치는 중에 발밑이 흔들리면 무엇 때문에 성적이 변했는지 알 수 없다.
`docs/27` 의 셈법 고침도 여기서 함께 반영됐다(2,142개 중 266개 등급 이동).

**② `fame` 을 원값으로 폈다.** `log(1 + 언어판) / log(101)`.
만점 자리를 40 으로 뒀더니 위가 통째로 동점이 되어(열 곳) 그 위는 `why`
길이 몇 자로 갈렸다 — 레알 알카사르가 엘체 야자수 숲 뒤 21위. 100 으로
바꾸니 동점이 사라지고 알함브라 2위 · 세비야 대성당 5위로 제자리.

**③ `vetted` 의 상수 둘을 `why` 깊이로 바꿨다.**
`0.3 × guide + 0.7 × clamp((why길이 − 45) / 55, 0, 1)`.
`named`(92% 보유)·`anyInfo`(89% 보유)는 상수라 순위를 못 갈랐다.

**④ `guide` 를 명성 18 이상에는 묻지 않는다.** `guide`(위키보이지 등재)는
사실 **수집 경로**다. 같은 도시 안에서 언어판 수를 맞춰 놓고 대표 비율을
견주면 무명 구간에서는 갈라 주지만(3~7: 18.5% ↔ 2.5%) 유명 구간에서는
거의 같다(18 이상: 30.0% ↔ 26.7%). 그 위에서 벌을 주면 **알함브라가
29위로 밀렸다** — 언어판 91개인데 위키보이지 목록이 아니라 '대표 명소
확인' 경로로 들어왔다는 이유로. 헤라클레스의 탑이 알함브라와 메스키타
위에 서는 순위였다. 18 위로 면제하니 정답지 성적은 그대로인 채
알함브라가 7위(만점 자리를 고친 뒤 2위)로 올라오고 도시 값어치 표도
**오히려 더 잘 맞는다.**

**⑤ `RANK_FLOOR` 을 다시 실측했다.** 0.45 → **0.385**.
예전 보정표를 목표로 두고 0.10~0.70 을 훑었다.

### 성적

| | 예전 | 지금 |
|---|---|---|
| 대표가 상위 10% | 49% | **57%** |
| 상위 25% | 68% | **85%** |
| 하위 절반으로 밀림 | 19% (28곳) | **3% (5곳)** |
| 평균 백분위 | 22% | **13%** |
| 점수 가짓수 | 25가지 | **91가지** |
| 가장 큰 덩어리 | 520곳 (32%) | **154곳 (9%)** |
| 기준선 통과 | 420곳 | 418곳 |

도시 값어치(왼쪽이 예전):

```
마드리드 10.9 → 10.2 · 바르셀로나 9.6 → 9.5   상한 4일에 걸림
세비야 3.3 → 4.1 · 빌바오 3.5 → 3.2 · 그라나다 3.0 → 3.1
톨레도 2.2 → 2.4 · 코르도바 1.7 → 1.9 · 말라가 1.4 → 1.2
세고비아 0.9 → 0.9 · 론다 0.5 → 0.5 · 네르하 0.4 → 0.4
```

**이 숫자를 그대로 믿으면 안 된다.** `why` 와 `highlights` 는 같은 손이
썼다. 딴 손의 잣대(언어판 수를 정답지로 두고 `fame` 을 뺀 채)로도 쟀고
거기서도 나아진다 — 상위25% 44 → 48% · 평균 38 → 36%. **폭은 훨씬 작다.**

### 되돌려 확인한 것

| 망가뜨린 것 | 걸리나 |
|---|---|
| 순위를 통째로 뒤집음 | ✓ 상위10% 57→1% |
| `fame` 을 상수로 | ✓ 57→45% |
| `vetted` 를 예전으로 | ✓ 57→52% · 하위밀림 3→15% |
| `why` 깊이만 빼기 | ✓ 57→50% · 하위밀림 3→13% |
| `fame` 을 5칸 등급으로 | ✓ 상위25% 85→81% · 평균 13→15% |
| `UNKNOWN_FAME` 0.24 → 0 | ✓ 상위25% 85→82% |
| 둘 다 예전으로 | ✓ 다섯 건 전부 (계단 22% 로 복귀) |
| `purpose` 끄기 | ✗ 반응 없음 (그 항이 순위를 안 가른다) |

### 곁다리로 나온 화면 고장

그라나다 값어치가 3.0 → 3.1 이 되자 3단계 일수 조절기의 ＋ 가 잠겼다.
천장을 눈금(0.2일) **아래로 내림**하고 있어서, 값어치가 눈금에 안 떨어지면
꼭대기(3.2일 16곳)에 갔다가 − 로 3.0(15곳)에 내려온 뒤 못 돌아왔다.
위 눈금으로 **올림**으로 바꿨다. `verify` 가 잡았다.

## 4단계 — 문턱 조정 · **3단계에 흡수됨 · 로그로뇨는 데이터 문제**

- **로그로뇨형** (예전 520곳 · 29개 도시): 계단이 사라져 없어졌다
- **산세바스티안형** (96곳 · 6개 도시): `guide` 면제(④)로 없어졌다

**로그로뇨는 점수로 못 고친다.** 재보니 원인이 달랐다.

| | |
|---|---|
| 볼거리 28곳 중 위키데이터 연결이 있는 것 | **0곳** |
| 등록부가 꼽은 대표 3곳이 데이터에 있는 것 | **0곳** |
| 최고점 | 0.355 (기준선 0.385) |

등록부는 `칼레 라우렐 · 리오하 와이너리 · 산타 마리아 대성당` 을 꼽았는데
데이터에는 `산타 마리아 데 팔라시오 성당` 과 이름 없는 와이너리들이 있다.
**이름이 안 맞아 `must` 가 하나도 안 붙는다.** 기준선을 내려 고치려면
다른 도시가 다 무너진다.

그리고 이것은 로그로뇨만의 일이 아니었다 — **등록부 대표 180개 중 31개
(17%, 23개 도시)가 데이터에 없다.** 조용히 사라지던 것이라 이제
`rank-truth` 가 세고, 더 늘면 걸린다.

**그래서 데이터 쪽을 고쳤다 → `docs/28`.** 등록부 이름 11개를 맞추고,
정말 없던 18곳을 손으로 넣고, `theme` 이 잘못 붙어 볼거리에서 빠지던
2곳을 고쳤다. 결손 31개 → **0개**, **로그로뇨 0일 → 0.7일(3곳).**

순위 엔진 작업은 여기서 끝난다.
