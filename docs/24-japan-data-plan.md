# 일본 — 도쿄부터. 정해진 것과 할 일

스페인을 1차로 마무리하고 일본을 붙인다. **스페인과 여행의 모양이 다르므로
데이터를 쓰기 전에 엔진을 먼저 고쳐야 한다.** 이 문서에 정해진 것이 다 있다.

---

## 1. 무엇이 다른가

| | 스페인 | 일본 (도쿄) |
|---|---|---|
| 기간 | 8~16일 | **최대 4박 5일** |
| 여행의 축 | 도시 사이를 옮겨 다닌다 | **도시 하나에 묵고 지역을 돈다** |
| 숙소 | 거점마다 옮긴다 | **한 곳에 고정** |
| '도시' 에 해당하는 단위 | 도시 (마드리드, 세비야) | **도쿄 안의 지역** (아사쿠사, 우에노) |
| 근교 | 톨레도·세고비아 | 하코네·가마쿠라 — 여기는 스페인과 같다 |

정리하면 **스페인의 도시 = 일본의 도시 내 지역**이고, 일본의 근교 도시는
스페인의 근교와 같은 층이다.

---

## 2. 정해진 것

### 2-1. 권역은 중심 도시 기준

**도쿄 · 오사카 · 후쿠오카 · 삿포로** 넷. 필요하면 나중에 추가.
**이번에는 도쿄만** 만든다.

### 2-2. 도시 등급 (`tier`)

```js
// 도시 — 잘 수 있는 곳
{ slug: 'tokyo',    tier: 'city',     name: '도쿄',     isHub: true }
{ slug: 'hakone',   tier: 'city',     name: '하코네',   nights: [1, 2] }
{ slug: 'kamakura', tier: 'city',     name: '가마쿠라' }

// 지역 — 도쿄 안. 자는 곳이 아니라 낮에 가는 곳
{ slug: 'asakusa',  tier: 'district', within: 'tokyo', name: '아사쿠사' }
{ slug: 'ueno',     tier: 'district', within: 'tokyo', name: '우에노' }
```

**`tier: 'district'` 는 절대 독립 숙박지가 되지 않는다.** `within` 도시의
숙소를 공유한다. 근교 도시(`tier: 'city'`)는 스페인의 섬처럼 **숙박이냐
당일치기냐를 엔진이 판단**한다.

`tier` 를 안 적으면 `'city'` 다 — 스페인 데이터는 손대지 않는다.

### 2-3. 문앞~문앞 오버헤드

지금은 **모든 구간에 +37분**(역까지 25분 + 도착역에서 12분)이 붙는다.
스페인 도시 간 이동에는 맞지만 지하철 한 정거장에는 말이 안 된다.

측정한 값 — 이것이 이 작업의 출발점이다:

| 구간 | 실제 | 지금 엔진 |
|---|---|---|
| 아사쿠사→우에노 (긴자선 2정거장) | 6분 | **43분** |
| 신주쿠→시부야 (야마노테선) | 7분 | **44분** |

**도시 내는 20분으로 한다.**

| | 분 |
|---|---|
| 출발지 → 역 도보 | 8 |
| 개찰·플랫폼·대기 | 6 |
| 탑승 | 등록부의 `transitMin` |
| 도착역 → 목적지 도보 | 6 |
| **오버헤드 합계** | **20** |

검산:

| 구간 | 등록부(역~역) | +20 | 실제 감각 |
|---|---|---|---|
| 아사쿠사→우에노 | 6 | 26분 | 걸어도 25분 |
| 신주쿠→시부야 | 7 | 27분 | 20~30분 |
| 시부야→긴자 | 17 | 37분 | 30~40분 |
| 신주쿠→아사쿠사 | 35 | 55분 | 45~60분 |

37분과 20분의 차이는 **역까지 여유를 두느냐**다. 신칸센·특급은 시간표가
정해져 있어 놓치면 큰일이라 25분 여유를 두지만, 지하철은 3분마다 오니
그럴 필요가 없다.

이 값은 **나라별 등록부에 둔다**(`COUNTRY.transferMin` 같은 자리).
오사카는 도쿄보다 작아 나중에 줄일 수 있어야 한다.

**등록부의 `transitMin` 은 '역에서 역까지'** 다(환승 도보 포함, 양 끝
도보·대기 제외). 지도 앱에서 역 이름으로 검색하면 나오는 그 값이다.

### 2-4. 온천 테마 추가

지금 테마 8개에 온천이 들어갈 자리가 없다. `onsen` 을 아홉 번째로 넣는다.

그런데 이건 표시만의 문제가 아니다. 거점 판정의 25%가
**"해가 진 뒤 할 것이 있는가"**(`basecity.ts` `eveningScore`)이고, 지금은
`nightlife` 와 `food` 로만 잰다. 온천을 여기 넣으면

- 하코네·구사쓰 → 저녁 콘텐츠가 있으므로 **숙박 추천**
- 가마쿠라·가와고에 → 낮 콘텐츠뿐이므로 **당일치기**

가 **특별 규칙 없이 그냥 나온다.** "온천은 숙박, 그 외는 대부분 당일치기"
가 바로 이것이다.

`planner.ts` 의 밤 시간대가 `nightlife` 만 받고 있으므로(`fitsSlot`),
온천도 받게 해야 한다 — 온천은 밤에 한다.

### 2-5. 화면 — 하루를 구간별로 그린다

지금 하루는 **평평한 목록**이다. 지역이 바뀌어도 아이템 사이에
`🚇 지하철·버스 약 18분` 한 줄뿐이라 어디서 어디로 넘어갔는지 안 보인다.

**데이터에는 이미 구간(`DayPlanSlot.segments`)이 있다. 화면이 안 쓰고 있을
뿐이다.**

```
2일차  2026-05-02 (화)                        🛏 신주쿠 (짐은 그대로)

┌ 아사쿠사 ─────────────── 🚇 긴자선 · 문앞~문앞 55분 ┐
   09:30  센소지
   11:00  나카미세 거리
└──────────────────────────────────────────────────┘
┌ 우에노 ──────────────── 🚇 긴자선 6분 · 문앞~문앞 26분 ┐
   13:00  우에노 공원
   14:30  도쿄국립박물관
└──────────────────────────────────────────────────┘
   ↳ 저녁은 신주쿠에서 · 🚇 25분
   19:30  오모이데요코초
```

표시를 늘리지 않고 **정리**한다.

| 무엇 | 어떻게 |
|---|---|
| 도시 간 이동 (도쿄→하코네) | 지금의 큰 `travel-block` 그대로 |
| 지역 간 이동 (아사쿠사→우에노) | **구간 머리줄** — 새로 만드는 것 |
| 같은 지역 안 (센소지→나카미세) | 지금의 한 줄(`cityMove`) 그대로 |

**스페인도 같이 좋아진다.** 날 모델을 바꾼 뒤로 스페인도 하루에 도시가 둘일
수 있는데(팔마→지로나→바르셀로나), 지금은 그것도 평평하게 나온다.

### 2-6. 철도 시간표 — 없이 시작한다

확인 결과:

| | 상태 |
|---|---|
| ODPT (公共交通オープンデータセンター) | 살아있음. **개발자 등록 후 API 키 필요** |
| `gtfs-data.jp` | 이 컨테이너에서 접속 불가 (차단인지 폐쇄인지 미확인) |

스페인이 Renfe 시간표를 쓰는 이유는 마드리드→세비야가 하루 몇 편뿐이고
막차를 놓치면 계획이 무너지기 때문이다. **도쿄 지하철은 3~5분 간격이라
시간표를 볼 이유가 없다.** 없어도 앱은 돌고 화면에 '추정치' 라고 표시된다.

필요해지면 하코네·닛코 같은 근교 노선만 나중에 채운다.

### 2-7. JR패스는 도쿄 것만

`transitGuide.passes` 는 **5단계 화면에만** 영향을 준다. 계획 계산에는
안 들어간다. 도쿄 4박5일에 JR 전국패스는 대개 손해이므로 **넣지 않는다.**
도쿄 서브웨이 티켓·스이카 같은, 실제로 이득인 것만 적는다.
오사카·도쿄를 잇는 여행이 생기면 그때 신칸센을 추가한다.

### 2-8. slug 표기

로마자, 소문자·숫자·하이픈만. `asakusa`, `kawaguchiko`, `shirakawa-go`.
파일 이름과 코드 참조에 그대로 쓰이므로 **한 번 정하면 바꾸기 번거롭다.**

## 3. 할 일 — 이 순서로

### ① 온천 테마 (가장 작고 독립적)

- `src/types.ts` `ThemeId` 에 `'onsen'`
- `src/lib/themes.ts` 에 한 줄 (`♨️ 온천`)
- `src/lib/store.ts` `DEFAULT_THEMES`
- `src/lib/basecity.ts` `eveningScore` — 온천을 저녁 콘텐츠로 센다
- `src/lib/planner.ts` `fitsSlot` — 밤 시간대가 온천을 받게
- `pipeline/src/extract.mjs` — 분류 regex(`onsen|hot spring|温泉`)와 `DURATION`

**검사**: `taste-check`(취향 역산), `basing-check`(거점 판정).
온천을 넣기 전/후로 하코네가 당일치기→숙박으로 바뀌는지 확인한다.

### ② 지역 등급 + 오버헤드 (여기서 도쿄 모델이 성립한다)

- `src/types.ts` `City` 에 `tier?: 'city' | 'district'`, `within?: string`
- `src/lib/basecity.ts` — district 는 거점 후보에서 제외, `within` 도시에 붙인다
- `src/lib/routing.ts` `measuredService` — 오버헤드를 인자로 받는다
  (도시 간 37 / 도시 내 20). 지금은 37이 박혀 있다
- 나라별 값을 `CountryIndex` 로 실어 나른다

**검사**: 새 `district-check.mjs` — 지역은 절대 숙박지가 안 되는가,
지역 간 이동이 실제 감각과 맞는가(위 검산표), 한 날에 지역 둘 이상이
들어가는가. 되돌려서 걸리는지 확인한다.

### ③ 구간별 화면

- `buildDay` 가 각 `PlanEntry` 에 구간 번호를 찍는다
  (지금은 `segIdx` 를 안에서만 쓰고 버린다)
- `Step5Plans` 가 구간별로 묶어 그린다
- 구간 머리줄에 그 구간으로 들어오는 이동을 적는다

**검사**: `verify.mjs` 에 절 하나. 스페인 228건이 그대로 통과해야 한다
(스페인도 하루에 도시 둘인 날이 있으므로 여기서 회귀가 잡힌다).

### ④ 도쿄 등록부

- `pipeline/registry/japan.mjs` — 도쿄 지역 + 근교 도시, 실제 이동 시간
- `pipeline/registry/japan-character.mjs` — 성격 프로필, 권역, 온천 태그
- `node pipeline/collect.mjs japan`
- `src/lib/countries.ts` 의 japan 을 `status: 'ready'` 로
- `src/lib/outlines.ts` 에 일본 국경선 (범위 `FRAMES.japan` 은 이미 있다)
- `npx tsx scripts/country-check.mjs` — 나라가 둘이 되면 이 검사가
  **서로 새지 않는지**까지 본다. 지금은 그걸 볼 수 없다

## 4. 하지 않아도 되는 것

- 화면 1~3단계 — 그대로
- 계획 엔진의 날 나누기(`daypack`) — 그대로. 하루에 여러 곳은 이미 된다
- 지도 코드 — 국경선이 없어도 도시 좌표로 그린다

## 5. 규모 감각

스페인 기준: 등록부 348줄 + 성격 562줄을 **사람이 썼고**, 결과가 도시 60곳 ·
아이템 2,132개 · 2.3MB 다. 아이템 설명(요약·왜 가는가·실무 정보·주의점)은
전부 한국어로 직접 썼다. 도쿄는 지역 8~12곳 + 근교 6~10곳 정도로 시작하면
스페인보다 작지만, **①~③ 엔진 작업이 먼저다.**

## 6. 이 판단의 근거

엔진에 도쿄 모델을 실제로 넣어 돌려 본 결과다.

```
경로: 신주쿠🛏 시부야🛏 긴자🛏 우에노🛏 아사쿠사🛏   ← 도쿄 안에서 호텔 5번 이동
1일  신주쿠 180분 + 시부야 180분  [자는 곳 시부야]
4일  긴자 180분 + 우에노 180분    [자는 곳 아사쿠사]
```

숙소를 강제로 신주쿠 한 곳에 고정하면 숙박 문제는 사라지지만, 이번에는
왕복이 부풀어 **4박5일이 6일로** 늘어난다(아사쿠사·우에노·긴자가 각각
하루씩 먹는다 — 서로 6~17분 거리인데도).

그래서 데이터보다 엔진이 먼저다.
